# Proxmox VE Automation Surface & Fleet Topology

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

Proxmox VE 9.x has closed almost all of the historical SSH-only gaps for this use case: qcow2 golden images can be uploaded or pulled by URL into an "import"-typed storage and attached at VM-create time via import-from, host bonds/VLAN-aware bridges/ZFS pools/storages are all creatable and live-applyable via the REST API, and the automated installer (answer.toml + proxmox-auto-install-assistant) covers disk selection by serial/model, static or DHCP network, ZFS mirror with ARC cap, first-boot hooks, and HTTP answer fetch keyed on DMI system info. The residue that still needs SSH/firstboot is host OS tuning (CPU governor, ethtool/sysctl, GRUB serial console for OpenGear, package installs) and snippets upload. For a pair of SE350s with no shared storage and VM-level redundancy, a two-node corosync cluster is actively harmful (quorum loss blocks VM autostart on the survivor); standalone nodes modeled as a pair in Nautobot, plus optional Proxmox Datacenter Manager 1.1.x (stable since Dec 2025) for fleet visibility, is the right topology.

## Key Findings

- proxmoxer is alive and healthy: v2.3.0 released 2026-03-04, active repo, no known CVEs; backends are https (default), openssh, paramiko, local. API tokens are supported only on the https backend for PVE/PBS (syntax: ProxmoxAPI(host, user='svc@pve', token_name='nautobot', token_value='<uuid>')); password auth issues 2-hour tickets that proxmoxer auto-renews on activity. verify_ssl accepts False or a CA-bundle path (passed through to requests).
- API tokens are NOT identical to their owning user: a token for root@pam still gets '500 Only root can pass arbitrary filesystem paths' when using import-from with an absolute path (confirmed in community.proxmox issue #243 and Proxmox forum). The supported non-root path is: put the image on a storage with content type 'import' and reference it by volume ID (e.g. scsi0='local-lvm:0,import-from=local:import/pa-vm-11.2.qcow2').
- Full qcow2 import is now pure-API in PVE 9.x (capability landed PVE 8.4/9.0): (a) POST /nodes/{node}/storage/{storage}/download-url with content=import (also iso, vztmpl) + checksum/checksum-algorithm — the NODE fetches the URL; or (b) POST .../storage/{storage}/upload with content=import for qcow2/vmdk/raw; then VM create/config with import-from. qm importdisk over SSH is no longer required.
- Everything in the VM lifecycle this project needs is API-settable in one create call or later config PUTs: net0='virtio,bridge=vmbr0,tag=123' or trunks=vlan;vlan lists for trunk vNICs, serial0=socket (plus vga=serial0 for serial-primary VNFs), onboot=1, startup='order=N,up=S' (boot ordering between PA-VM/C8000v/jumphost), cpu=host, resize (PUT /nodes/{n}/qemu/{vmid}/resize), clone (POST .../clone), template conversion (POST .../template), CDROM attach for bootstrap ISOs (ide2='local:iso/bootstrap.iso,media=cdrom').
- Since PVE 8.0, attaching a vNIC to ANY bridge as a non-root user requires SDN.Use on /sdn/zones/localnetwork/<bridge> (or /sdn/zones/localnetwork for all) — e.g. via built-in PVESDNUser role — in addition to VM.Config.Network. This applies even when the SDN feature is unused and is the most commonly missed privilege (403s). A working automation-role privilege set (community/Terraform consensus): VM.Allocate, VM.Clone, VM.Config.*, VM.PowerMgmt, VM.Audit, VM.Console, Datastore.AllocateSpace, Datastore.AllocateTemplate (needed for upload/download-url), Datastore.Audit, Sys.Audit, SDN.Use; grant to the token itself when privilege separation (privsep=1) is on.
- Host network config is API-driven and live: POST /nodes/{node}/network creates bond (bond-mode 802.3ad, xmit-hash-policy) and VLAN-aware bridge (bridge_vlan_aware, bridge-vids 2-4094) interfaces; PUT /nodes/{node}/network applies via ifupdown2 reload (ifupdown2 default since PVE 7.0, no reboot). Storage bring-up is also API: /nodes/{node}/disks/zfs|lvm|lvmthin|directory to create pools + /storage to register them; /nodes/{node}/apt/repositories, /nodes/{node}/time, DNS, certificates all have endpoints.
- Still SSH/firstboot-only (no API): arbitrary package install (apt API only updates index/lists repos), CPU governor/power tuning, ethtool NIC tuning, sysctl/hugepages/kernel cmdline, GRUB serial-console redirect for the OpenGear path, and uploading 'snippets' content (cloud-init cicustom files cannot be pushed via API — a long-standing gap; the built-in cloud-init keys ciuser/cipassword/sshkeys/ipconfigN ARE API-settable and avoid snippets for the Ubuntu jump host).
- Proxmox templates/images are strictly per-node without shared storage; linked clones require the template on the same storage. Distribution patterns: internal HTTP(S) image repo + download-url with SHA256 checksum (pure API, works standalone — recommended); pvesr/ZFS replication requires a cluster AND ZFS; PDM (as of 1.1.x) does NOT distribute images. Deploying directly from the imported qcow2 (import-from at create) each time removes the need to maintain converted VM templates per node at all.
- Two-node cluster mechanics (official pvecm docs): losing the peer drops quorum, pmxcfs goes read-only, and guests — including onboot autostart after a site power event — will not start ('cluster not ready - no quorum (500)'); pvecm expected 1 is a manual, non-persistent workaround; the only real fix is a third voter (QDevice needs an external always-on box with root SSH access to it). Also: joining a node that already has VMs into a cluster is unsupported (/etc/pve is overwritten). Corosync wants <5 ms latency and stable links.
- Proxmox Datacenter Manager status: stable 1.0 released 2025-12-04; current 1.1.7 (May/Jul 2026), Rust API + CLI + web UI. Manages both clusters and standalone nodes: unified VM list, start/stop/snapshot, update overview, remote shell, ACME, LDAP/OIDC/AD auth, API tokens, and cross-remote live migration (bandwidth limits, target selection). Enrollment uses a PVE-side API token; forum-reported 403s during add-remote trace to missing Sys.Audit (PVEAuditor-level read at /) on that token; more privileges needed for lifecycle actions. PDM makes the standalone-pair topology operationally viable at fleet scale without corosync.
- Automated install in VE 9.x: answer.toml with [global] (fqdn, root password/hash, SSH keys, timezone, subscription-key staging), [network] (from-dhcp or from-answer with cidr/gateway/dns + udev-property filters), [disk-setup] (filesystem ext4/xfs/zfs/btrfs, disk-list or filters on ID_SERIAL/ID_MODEL with wildcards and filter-match any/all, zfs.raid raid0/1/10/z1-3 + arc-max + compression + ashift, lvm swapsize/maxroot/maxvz/minfree), [post-installation-webhook] (JSON POST with cert fingerprint + auth token), [first-boot] (script from-iso or from-url, ordering before-network|network-online|fully-up, 1 MiB max). Fetch modes: baked into ISO, labeled partition 'proxmox-ais', or HTTP(S) — URL from ISO, DHCP option 250, or DNS TXT proxmox-auto-installer.{search-domain}; the HTTP fetch POSTs the machine's DMI/system info so a small service can render a per-node answer.toml keyed on serial/MAC (this is exactly the 'generic ISO + lookup service' option in the colleague's open decision). proxmox-auto-install-assistant provides prepare-iso, validate-answer, device-info, device-match, system-info, inspect-iso.
- VE 9.x version-specific installer/platform notes: 9.0 is Debian 13 'Trixie'; answer.toml keys moved to kebab-case (snake_case deprecated); 9.1 added NIC name pinning in the answer file (stable interface names across kernel updates — also available post-hoc via pve-network-interface-pinning tool); 9.2 added PXE/iPXE ISO prep (proxmox-auto-install-assistant --pxe), HTTP answer-fetch auth tokens, and full-disk LUKS.
- Storage engine facts for a single NFV node: the installer's only native software mirror is ZFS RAID1 (btrfs RAID1 exists but tech-preview); ext4/xfs go on LVM+LVM-thin on a single disk (or hardware RAID LUN). PVE installer ZFS ARC default since 8.1 (still in 9.x): 10% of RAM clamped to 16 GiB, written to /etc/modprobe.d/zfs.conf, and settable explicitly via zfs.arc-max in answer.toml. LVM-thin: raw block, near-zero RAM overhead, snapshot support, no checksumming/self-heal. Directory+qcow2: simplest, file-layer overhead, qcow2 snapshots. 'Snapshots as volume chains' for LVM-thick/dir is tech preview in 9.x — avoid. ZFS costs for realtime VNFs: ARC RAM competition, CoW/sync-write latency and CPU — controllable by pinning arc-max low, and mostly irrelevant to steady-state VNF traffic (VNFs do little disk I/O after boot).
- Ansible ecosystem: Proxmox modules were extracted from community.general into the dedicated community.proxmox collection (0.1.0 in May 2025 from community.general 10.6.0; now 2.x); community.general.proxmox_* redirects are deprecated and removed in community.general 15. Community host-config practice is Ansible-over-SSH or firstboot scripts for the host layer, proxmoxer/Terraform/Ansible over the API for the VM layer.

## Recommendations for This Project

- Run the SE350 pairs as two standalone PVE nodes, not a cluster: no shared storage, redundancy is already at the VM level, and a 2-node cluster's quorum behavior (survivor refuses VM autostart after a power event when its peer is dead) is precisely the failure mode an unattended edge site cannot tolerate; a QDevice would require a third always-on box per site. Model the pairing ('server 1'/'server 2') purely in Nautobot.
- Adopt PDM 1.1.x early but only for fleet visibility/ops (unified inventory, updates, remote shell) — keep all deployment automation pointed at each node's own API; PDM is young (stable ~8 months) and adds no image-distribution or config-push capability yet. Fix the colleague's enrollment 403 by granting the PDM token Sys.Audit at / (start from PVEAuditor) and layering action privileges only as needed.
- Standardize on proxmoxer (https backend) + API token with privilege separation for the Nautobot Job service account; create a custom role ≈ {VM.Allocate, VM.Clone, VM.Config.*, VM.PowerMgmt, VM.Audit, VM.Console, Datastore.AllocateSpace, Datastore.AllocateTemplate, Datastore.Audit, Sys.Audit, SDN.Use} with SDN.Use granted on /sdn/zones/localnetwork — and store the token in Nautobot Secrets like the XCC creds. Distribute the node's self-signed CA (or ACME certs) so verify_ssl can point at a CA bundle instead of False.
- Golden-image pipeline: run an internal HTTPS image repo with immutable versioned filenames + SHA256 sidecars (e.g. pa-vm-flex-11.2.4-1.qcow2); enable an 'import'-typed storage on every node; Nautobot Job calls download-url (content=import, checksum) then creates VMs with import-from volume IDs — fully API-driven, no SSH, no per-node template maintenance, and Nautobot config context holds the VNF-type → image-URL/checksum mapping as SoT.
- Choose ONE VLAN-aware bridge on the LACP bond (bond0, 802.3ad → vmbr0 bridge-vlan-aware, bridge-vids <site range>) rather than replicating ESXi port-group-per-VLAN as bridge-per-VLAN; per-VM access VLANs via net tag= and trunk interfaces for PA-VM/C8000v via trunks= — all API-settable and matching the Nautobot IPAM/VLAN model cleanly.
- Resolve the colleague's ISO decision toward: one generic prepared ISO per PVE minor release + HTTP answer fetch, with a small answer-service (can be a Nautobot Job endpoint or tiny Flask/lookup service) rendering answer.toml.j2 from Nautobot data keyed on the DMI serial the installer POSTs; the ISO already supports pinned cert fingerprint + auth token (9.2). This removes the per-node ISO build step from the pipeline and matches all three scenarios (lab as-built, field redeploy, lab rebuild).
- Split post-install config into three explicit layers in proxmox-config/: (1) firstboot hook (minimal: get bond/bridge + mgmt IP up, enable root SSH key, phone-home webhook); (2) API layer from the Nautobot Job (bridges/bonds via /nodes/{n}/network + reload, storage creation, repo config, import storage, VM deploys); (3) a small SSH layer (paramiko or community.proxmox-era Ansible) ONLY for the residue: performance governor, ethtool/sysctl NIC tuning, GRUB serial-console for OpenGear, extra packages. This mirrors the ESXi 'robot' but with a much smaller SSH surface.
- Storage layout: if the SE350s have the M.2/RAID mirroring hardware option, use ext4+LVM-thin on the mirrored LUN (lowest RAM/CPU tax for realtime VNFs, snapshots included); if mirroring must be software, use installer-native ZFS RAID1 with zfs.arc-max pinned explicitly (4–8 GiB) in answer.toml and that amount subtracted from the VM RAM budget. Either is fine because VM-pair redundancy makes per-node storage resilience a convenience, not a survival requirement — do not build anything on the 9.x 'volume chain snapshot' tech preview.
- For the Ubuntu jump host use built-in cloud-init via API (ciuser/sshkeys/ipconfig0 + cloudinit drive) and avoid cicustom/snippets entirely (snippets can't be uploaded via API); for PA-VM and Cisco VNFs use bootstrap/day-0 ISOs uploaded through the storage upload API (content=iso) — both keep the deploy path SSH-free.

## Pitfalls & Gotchas

- import-from with an absolute filesystem path fails for ALL API tokens including root@pam's ('Only root can pass arbitrary filesystem paths') — it works only with root@pam password/ticket auth; design around import-storage volume IDs from day one.
- SDN.Use on /sdn/zones/localnetwork/<bridge> (PVE 8+) is required for a non-root token to attach/modify vNICs even with VM.Config.Network — the classic silent-403 that breaks Terraform/Ansible/proxmoxer VM creation.
- download-url makes the PVE NODE fetch the image: edge nodes need reachability (and cert trust, or verify-certificates=0) to the image repo — a shipped/as-built lab flow must host the repo somewhere the lab AND field nodes can reach, or fall back to the upload endpoint (which streams through pveproxy and is slow/tmp-space-bound for multi-GB images).
- Two-node cluster quorum: onboot autostart is blocked on the survivor when the peer is down (pve-guests waits for quorum; pmxcfs read-only); pvecm expected 1 must be re-run after every reboot — do not let 'cluster for convenience' sneak into the design; also, joining an in-service node with existing VMs into a cluster later effectively requires evacuating it (/etc/pve gets overwritten), so the topology decision is one-way for scenario 2 (field redeploys on in-service hosts).
- PVE 9 answer.toml uses kebab-case keys (snake_case deprecated) — 8.x examples on the web silently mismatch; always run proxmox-auto-install-assistant validate-answer in CI against the template output.
- First-boot hook executable is capped at 1 MiB and runs once — keep it a bootstrap shim that fetches the real config, not the config itself; scripts need shebangs and binaries must be static x86_64.
- Snippets content (cloud-init cicustom) has no upload API — any design that assumes pushing user-data files to nodes reintroduces SSH/scp into the hot path.
- proxmoxer API tokens don't work on the SSH backends; and with privsep=1 (default) the token's OWN ACLs govern — granting the role to the user but not the token yields confusing 403s.
- NIC names can shift across kernel/driver updates breaking bond/bridge configs; use answer-file interface pinning (9.1+) or pve-network-interface-pinning / systemd .link files as part of install, especially on an EOL platform like SE350 where NIC enumeration quirks won't get firmware fixes.
- Host serial redirect for OpenGear (GRUB console=ttyS0 + serial-getty) and VM serial (serial0=socket) are different layers — the VM side is API-clean, the host side is SSH/firstboot-only; don't expect the API to cover the emergency-console requirement.
- PDM cross-remote migration of local-storage VMs exists but is built on the still-maturing remote-migration path — treat it as an ops convenience, never as the redundancy mechanism.
- ZFS ARC interactions changed with OpenZFS 2.3/2.4 in PVE 9 (forum reports of different effective defaults/reclaim behavior) — never rely on defaults on a RAM-budgeted NFV host; set zfs.arc-max explicitly at install time.

## Open Questions

- Do these specific SE350 units have the ThinkSystem M.2 mirroring enablement kit / any hardware RAID, or only single/independent disks? This is the deciding input between ext4+LVM-thin (HW mirror) and ZFS RAID1 (software mirror) — needs hardware-dimension confirmation before the answer.toml disk-setup template is written.
- Exact minimal privilege set for PDM add-remote (the colleague's 403 issue): forum evidence points to Sys.Audit at / plus per-action privileges, but the precise scoped set for PDM 1.1.7 should be verified in the lab rather than granting PVEAuditor at / permanently.
- Whether the SE350's DMI system-serial as POSTed by proxmox-fetch-answer matches the serial recorded in Nautobot (keying for the answer-service); verify with proxmox-auto-install-assistant system-info on real hardware.
- Behavioral validation that net trunks= on a VLAN-aware Linux bridge delivers correct multi-VLAN trunking to PA-VM and C8000v (LLDP/CDP, native VLAN handling) versus giving each VNF multiple access-tagged vNICs — needs lab packet-level testing.
- Which PVE 9.x point release to freeze on for the golden ISO (9.2 is current per the roadmap with the newest installer features — PXE prep, HTTP fetch auth token — but the team should pin one and track ISO re-prep cadence per point release).
- Whether the SE350's older CPU (Xeon D-2100) plus PVE 9 kernels (6.14+/6.17) have any driver regressions for its NIC options — EOL hardware on a new Debian 13 base warrants a burn-in before fleet rollout.
- download-url reachability model for scenario 1 (as-built in lab, then shipped): does the image repo remain reachable from field sites for scenario 2 redeploys, or does each site need a local mirror/the Nautobot Job to fall back to upload?
