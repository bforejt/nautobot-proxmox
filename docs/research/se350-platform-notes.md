# Lenovo ThinkEdge SE350 Platform Notes

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

The original SE350 (Xeon D-2100, machine types 7Z46/7D1X/7D27) is a first-generation-XCC platform: Redfish virtual media works but only via the XCC1 mechanics (PATCH on an EXT{N} VirtualMedia member, HTTP or credential-less NFS only) and only with the XCC Enterprise Feature-on-Demand license active — the colleague's SE455-V3-targeted client (POST InsertMedia) will need a second code path plus member selection by EXT prefix. BIOS (Maximum Performance mode, C-states, serial console redirect) is settable via the standard Redfish Bios/Settings pending-PATCH flow using Lenovo's menu-name-derived attributes (e.g. OperatingModes_ChooseOperatingMode=MaximumPerformance). Hardware is Proxmox-friendly (integrated Intel X722 10GbE/i40e, I350 1GbE/igb, all-M.2 storage, a physical rear RJ45 serial port for OpenGear), with the main gotchas being the X722 firmware LLDP agent vs LACP, the Marvell 88SE9230 M.2 boot "RAID" (prefer ZFS mirror), and — if their units are the "with Security Pack" variant — ThinkShield locked-state activation and motion-triggered SED lockup, which directly affects the ship-after-lab-build and replacement-rebuild scenarios. SE350 was withdrawn from marketing in 2025 and the SE350 V2/SE360 V2 successors are already withdrawn too (as of 2026); SE455 V3 remains current, validating the colleague's target and arguing for a per-platform abstraction layer (vmedia method, BIOS attribute map, disk/NIC selection) rather than SE350-only logic.

## Key Findings

- XCC generation/licensing: SE350 uses first-gen XClarity Controller (XCC1, documented by pubs.lenovo.com/xcc-restapi). Base is XCC Standard; XCC Advanced FoD adds remote KVM only; XCC Enterprise FoD adds remote KVM + ISO/IMG virtual-media mounting + power capping. Redfish virtual media on SE350 therefore requires the Enterprise FoD upgrade; without it the EXT media members simply do not appear in the VirtualMedia collection (confirmed pattern for XCC1 platforms in Red Hat article on SE450/SR630 V2 Redfish vmedia readiness, access.redhat.com/articles/6958685).
- XCC1 virtual media mechanics (differs from colleague's SE455 V3 client): documented method is PATCH https://<bmc>/redfish/v1/Managers/1/VirtualMedia/EXT{N} with body {Image: <url>, Inserted, WriteProtected}; eject = PATCH Image:null. Only EXT{N} members can be inserted via Redfish, and only via HTTP or credential-less NFS (no HTTPS-with-auth, no CIFS/SFTP via this path). RDOC members (50 MB cap) and Remote{N} (browser-only) cannot be Redfish-inserted. Lenovo's official example (lenovo_mount_virtual_media.py in lenovo/python-redfish-lenovo) uses PATCH for '19A'+ XCC firmware (10 predefined VirtualMedia members) and POST InsertMedia only for older 18D firmware and AMD TSM boxes — the reverse of DMTF-standard expectations.
- Red Hat's Lenovo vmedia-readiness matrix (SE450: BMC >= 1.00 USX302R; SR630 V2: BMC >= 1.65 AFBT18J) confirms firmware minimums exist per XCC1 model for reliable Redfish vmedia; no SE350-specific minimum build is published — treat 'latest available XCC firmware' as the requirement and lab-verify.
- BIOS via Redfish: yes on SE350 — standard pending-settings flow (GET /redfish/v1/Systems/1/Bios for current values and exact attribute names; PATCH /redfish/v1/Systems/1/Bios/Settings; changes apply at next reboot). Lenovo Redfish attribute names are UEFI menu names with underscores: OperatingModes_ChooseOperatingMode with values including MaximumPerformance (naming convention confirmed in Lenovo tuning guides LP1836/LP1977). SE350 operating modes per the Edge UEFI manual (pubs.lenovo.com/uefi_iot): Minimal Power / Efficiency-Favor Power / Efficiency-Favor Performance (default) / Maximum Performance / Custom Mode; C-States (default Autonomous), Turbo, P-state control, Power/Performance Bias etc. are individually settable only in Custom Mode — presets lock them.
- Serial console: SE350 has one physical rear RJ45 serial port (product guide LP1168; port default listed at 9600 baud) — OpenGear attachment is possible without relying on XCC SOL. UEFI Console Redirection settings (uefi_iot manual): COM Port 1/2 (Enable default), Console Redirection (Auto default), Serial Port Sharing (Disable default), Serial Port Access Mode (Disable default), COM1 baud default 115200, ANSI default emulation. XCC SOL exists as a secondary path (IPMI SOL / SSH to XCC). For host-owned serial (OpenGear), keep Serial Port Sharing/Access Mode at Disable and configure Proxmox GRUB/getty for ttyS0.
- CPU/RAM: single soldered Intel Xeon D-2100 (Skylake-D SoC): D-2123IT 4c/2.2GHz/60W, D-2143IT 8c/2.2/65W, D-2163IT 12c/2.1/75W, D-2166NT 12c/2.0/85W, D-2183IT 16c/2.2/100W; all with VT-x/VT-d, HT, turbo to 3.0GHz. 4 DIMM slots (1DPC, 4 channels), max 256 GB DDR4-2666 (runs at 2400 due to CPU). TPM 2.0 integrated; Secure Boot supported.
- Networking: network-module based. 10G SFP+ wired module = 2x SFP+ from the SoC-integrated Intel X722 (i40e driver, iavf for SR-IOV VFs) + 2x 1GbE RJ45 Intel I350 (igb) + 2 dedicated RJ45 XCC management ports (redundant or daisy-chain up to 7 nodes, NC-SI shared option). A 10GBASE-T module variant exists; the wireless/LTE module was withdrawn earlier. This means 10G NIC silicon is on-package and identical across all SE350s — NIC naming is stable within the platform.
- Storage: all M.2, no 2.5-inch bays. Boot: single M.2 SATA (plain AHCI) or dual M.2 SATA on a Marvell 88SE9230 adapter (RAID 0/1, UEFI boot only). Data: up to 8x M.2 SATA/NVMe via two 4-bay riser adapters — NVMe RAID only via Intel RSTe/VROC, SATA RAID via 88SE9230; ~16 TB max NVMe. SED drives supported (with automatic AK management on Security Pack units).
- Proxmox VE 9 compatibility: PVE 9.0 (released 2025-08-05) = Debian 13 'Trixie', kernel 6.14.8-2, QEMU 10.0.2, ZFS 2.3.3. Skylake-D, X722 (i40e), I350 (igb), AHCI and NVMe are all mature in-kernel; no SE350-specific blockers found in Proxmox forums. Lenovo even publishes a Proxmox install white paper (LP2218, 'Installing Proxmox VE 8.4 on Lenovo ThinkSystem Servers', May 2025), though Proxmox is not on the SE350 OSIG certified-OS list (ESXi/RHEL/SLES/Windows/Ubuntu are).
- X722 LLDP gotcha (matters for their LACP dot1q-trunk LAGs): Intel 700-series NICs have an on-chip firmware LLDP agent that consumes inbound LLDP frames before the OS sees them, breaking LLDP neighbor visibility and interfering with LACP-related tooling. Disable per port: ethtool --set-priv-flags <if> disable-fw-lldp on (persist in /etc/network/interfaces post-up). X722 support for this priv-flag requires reasonably new NIC firmware (X722 LLDP-disable support arrived around FW 3.10 era).
- Security Pack variants: SE350 shipped as standard and 'with Security Pack' (machine types among 7Z46/7D1X/7D27). Security Pack units ship in a LOCKED state and must be claimed/activated via ThinkShield Key Vault Portal or ThinkShield Edge mobile app (machine type + serial + secure activation code) before they will boot; SED data access auto-locks on tamper events; motion detection (G-sensor) and System Lockdown Mode exist only on Security Pack units. This directly affects scenario 1 (lab build then SHIP — motion during transit can trigger tamper/SED lock) and scenario 3 (replacement units arrive locked).
- EOL timeline: Lenovo internal training (DVEDG215, Sep 2024) states SE350 EOL as of March 2025; the LP1168 product guide records withdrawal from marketing effective 2025-05-23. Exact End-of-Service date is not published in searchable sources (Lenovo's HT504708 lookup tool is the authority); Lenovo convention is roughly 5 years of hardware support post-withdrawal (~2030).
- Succession reality (2026): BOTH SE350 V2 (Xeon D-2700, LP1676) and SE360 V2 (Xeon D-2700, LP1677) are already marked 'withdrawn product' on Lenovo Press; SE455 V3 (AMD EPYC 8004 'Siena', XCC2, 2U short-depth, LP1724) remains current with guide updates as recent as 2026-03-30. SE455 V3 is the natural successor — the colleague's repo target is correct.
- ESXi->Proxmox operational delta: Lenovo OneCLI officially supports RHEL 7-10, SLES 12-16, Ubuntu 18/20/22/24 — Debian is NOT in the support matrix, so in-band firmware updates on Proxmox are unsupported territory. Out-of-band alternatives: XCC web UI update, Redfish UpdateService (Lenovo HT511484), or bootable media updates. There is no XClarity integration for Proxmox (LXCI exists only for vCenter/Windows Admin Center); XClarity Administrator can still do OOB monitoring/firmware for the hosts.
- Secure Boot interplay: Proxmox ISO installs support Secure Boot via signed shim since PVE 8.1, but Debian-on-top and systemd-boot paths do not; the simplest fleet policy for the auto-install pipeline is Secure Boot disabled (settable via the standard Redfish SecureBoot resource or Lenovo Bios attributes), with TPM 2.0 left enabled (harmless to PVE).
- Colleague's xcc_client.py concrete gap for SE350: (a) mount_iso() POSTs to VirtualMedia.InsertMedia — XCC1 documents PATCH on the member instead; (b) _select_cd_media() picks the first CD/DVD-capable member — on XCC1 the collection has ~10 members (EXT1-4, RDOC1-2, Remote1-4) and selection must filter by Id prefix 'EXT', not MediaTypes, or it will pick a non-insertable member; (c) discovery-based path resolution (already present) is the right abstraction and carries over.

## Recommendations for This Project

- Make the BMC client dual-mode: after discovery, inspect the VirtualMedia collection — if EXT{N} members exist (XCC1/SE350) use PATCH-on-member with an EXT-prefix filter; else use POST InsertMedia (XCC2/SE455 V3). This is the single most important hardware-abstraction seam for reusing the colleague's job on SE350.
- Gate the deploy job on the XCC Enterprise FoD license: check for presence of EXT members (its observable symptom) and fail with an explicit 'XCC Enterprise license missing' error; inventory FoD keys per serial in Nautobot so field spares can be verified before shipment.
- Serve the Proxmox auto-install ISO over plain HTTP from the lab/site webserver — XCC1 EXT insert only supports HTTP or credential-less NFS, so do not design the answer-file/ISO service around authenticated HTTPS for the SE350 track.
- Implement BIOS policy as data, not code: a per-platform YAML attribute map in bmc/ (SE350: OperatingModes_ChooseOperatingMode=MaximumPerformance, console-redirect group under DevicesandIOPorts_*; SE455 V3: different AMD attribute names) applied through one generic Redfish Bios/Settings PATCH + reboot routine; first lab step is dumping GET /redfish/v1/Systems/1/Bios on a real SE350 to capture exact spellings.
- Serial/OpenGear plan: standardize 115200 8N1, keep UEFI Serial Port Sharing/Access Mode = Disable so the physical RJ45 stays host-owned, and have the firstboot hook add console=ttyS0,115200 to GRUB plus a serial getty — this reproduces the ESXi-era OpenGear emergency console on Proxmox.
- Prefer ZFS RAID1 across two M.2 boot devices (selected in answer.toml by size/model filter) over the Marvell 88SE9230 firmware RAID — the Marvell mirror is UEFI-boot-only fake-RAID that Linux tooling cannot health-monitor, and ZFS-mirror-by-filter keeps disk selection logic identical on SE455 V3; likewise expose data NVMe as JBOD + ZFS instead of VROC/RSTe.
- In proxmox-config, bond the two X722 SFP+ ports (LACP) under a VLAN-aware vmbr, and always set disable-fw-lldp on both 10G ports before trusting LLDP/LACP behavior — bake it into the network template, not a manual step.
- Treat SE350 sustainment as spares-based: CPU/NIC are soldered so stock whole-unit spares plus M.2/DIMM/power-adapter consumables; pin a known-good firmware bundle (XCC + UEFI + X722) in the repo and stop chasing updates, since the firmware stream will end with EOS (~2030, verify).
- Add a 'platform profile' concept to the job suite now (vmedia method, BIOS attribute map, disk filter, NIC naming, license requirements, activation steps keyed off Nautobot device-type) — with SE350 V2/SE360 V2 already withdrawn, the fleet will inevitably be mixed SE350 + SE455 V3, and per-platform if/else will rot fast.
- If any units are 'with Security Pack': write the ThinkShield claim/activation step into the scenario-3 (replacement) runbook and evaluate disabling motion-detection/tamper-lock before scenario-1 shipping, since transit G-sensor events can lock SED data access until portal reactivation.

## Pitfalls & Gotchas

- Without the XCC Enterprise FoD, virtual media fails silently-confusingly: the EXT members just don't exist in the Redfish collection, so a naive client sees only RDOC/Remote members and gets unhelpful errors on insert.
- The colleague's _select_cd_media() will mis-select on SE350: XCC1 exposes ~10 VirtualMedia members and MediaTypes metadata does not distinguish insertable (EXT) from non-insertable (RDOC/Remote) members — filter by Id prefix.
- XCC1 vmedia protocol ceiling: HTTP or credential-less NFS only. Any pipeline assumption of authenticated HTTPS ISO URLs breaks on SE350 (fine on XCC2/SE455 V3).
- Preset operating modes lock individual power settings: you cannot set MaximumPerformance AND separately force C-states — that combination requires CustomMode with each knob set explicitly; job logic must not PATCH individual Processors_* attributes while a preset mode is selected and expect them to stick.
- Marvell 88SE9230 M.2 boot RAID is UEFI-boot-only and opaque to Linux — an ESXi-era habit that produces an unmonitorable mirror under Proxmox.
- Intel X722 firmware LLDP agent eats LLDP frames and can disrupt LACP — and the disable-fw-lldp priv-flag itself depends on NIC firmware level; old X722 firmware may not honor it.
- Security Pack units: shipping a lab-built server (scenario 1) with motion detection enabled can trigger tamper/SED lockup in transit, requiring ThinkShield portal reactivation on arrival; replacement units (scenario 3) arrive in locked state and will not boot until claimed.
- Physical RJ45 serial port default is 9600 baud while the UEFI COM settings default to 115200 — mismatched assumptions will produce 'dead' OpenGear consoles; standardize explicitly.
- OneCLI does not officially support Debian, so the ESXi-era in-band firmware-update workflow has no direct Proxmox equivalent — plan out-of-band (Redfish UpdateService) from day one, and note NIC firmware may still require bootable-media updates.
- Proxmox is not OSIG-certified for SE350, so any residual Lenovo hardware support case can deflect on OS; keep an Ubuntu live-USB or ESXi-on-spare procedure for hardware fault isolation.
- Redfish BIOS changes are pending-until-reboot: jobs must sequence Bios/Settings PATCH -> reboot -> verify readback, or settings silently never apply.
- Virtual-media ISO streaming is pull-over-HTTP from the BMC for the whole install: over a WAN this is slow and fragile — do bare-metal installs only where the ISO webserver is LAN-adjacent (lab), which their scenarios already assume.

## Open Questions

- Exact SE350 End-of-Service date — Lenovo's HT504708 interactive lookup is authoritative; searchable sources only confirm EOL/withdrawal (Mar/May 2025). User should run the lookup against their machine types (7Z46/7D1X/7D27).
- Are their SE350 units standard or 'with Security Pack' (and is motion detection/tamper-lock currently enabled under ESXi)? This changes scenarios 1 and 3 materially.
- Do their units already have XCC Enterprise FoD keys (check XCC web UI > Server Management > licenses, or FoD inventory)? ESXi-era remote-console use suggests at least Advanced, but Enterprise is the vmedia requirement; are keys transferable to spare units?
- Does current (final) SE350 XCC firmware also accept the standard POST VirtualMedia.InsertMedia action in addition to the documented PATCH? Lenovo docs and samples say PATCH for XCC1 — lab-test both before hardcoding.
- Exact Redfish BIOS attribute names/values on SE350 (OperatingModes_ChooseOperatingMode is confirmed by convention; the DevicesandIOPorts_* console-redirect spellings and C-state value enums need a live GET /redfish/v1/Systems/1/Bios dump).
- Minimum SE350 XCC/UEFI firmware builds for reliable Redfish vmedia (the Red Hat matrix covers SE450/SR630 V2 only) — and what firmware level their fleet is actually on.
- RJ45 serial port pinout on SE350 vs OpenGear cabling (Cisco-rollover compatible or not) — trivial lab check, but blocks the console runbook.
- Whether XCC out-of-band update covers X722/I350 NIC firmware on SE350 or only XCC/UEFI (NIC firmware may require bootable media or an in-OS tool that Debian lacks).
- Does a proxmox-auto-install-assistant-modified PVE 9 ISO boot with Secure Boot enabled on SE350, or should the BIOS policy job disable Secure Boot fleet-wide (recommended default pending this test)?
- Which ESXi NIC tunings their current robot applies (ring sizes, interrupt moderation?) — needed to define the Linux/ethtool equivalents in proxmox-config rather than cargo-culting.
