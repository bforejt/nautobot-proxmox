# Nautobot Data Modeling & Job Architecture

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

Nautobot's "current" line in Aug 2026 is actually 3.x (3.0 GA 2025-11-17, 3.1 April 2026), with 2.4 as the LTM release; every app this project needs (SSoT, Golden Config, Device Lifecycle, Secrets Providers, Firewall Models, Design Builder) ships both a Nautobot-3 train and a 2.4-LTM train, so the platform version must be decided first. Core virtualization modeling still cannot pin a VirtualMachine to a specific host Device (VM belongs to exactly one Cluster), so the SE350 pair is best modeled as two one-host Clusters (or one Cluster plus a custom Relationship); VNFs should be VirtualMachines, with the caveat that Golden Config only targets dcim.Device. nautobot-app-design-builder is real and actively maintained (v3.1.0 released 2026-04-20) and its deployment/decommission lifecycle maps almost exactly onto the "site code + supernet + server1/2 → standard layout" problem, but it is niche (~15 stars) so phase 1 should be a hand-written Job with Design Builder evaluated as a spike. There is no official Proxmox SSoT integration — only two tiny community repos — and the official vSphere SSoT integration is the reference pattern if drift-sync from Proxmox is wanted later.

## Key Findings

- VERSION LANDSCAPE: Nautobot 3.0 released 2025-11-17 (Bootstrap 5.3 UI, Approval Workflows replacing Job.approval_required, Data Validation Engine merged into core, new Load Balancer and VPN models, Device.cluster FK replaced by many-to-many Device.clusters, Python 3.10-3.13, M2M fields excluded from REST API responses by default unless exclude_m2m=False). Nautobot 3.1 shipped/ships April 2026 (Job Console Logging, custom field scoping). Nautobot 2.4 (released 2025-01-10) is the LTM release; NTC apps state they support 'previous major release for users of Nautobot LTM 2.4 only with critical bug and security fixes'. The prompt's 'Nautobot 2.x era' framing is out of date for a greenfield Aug-2026 deployment.
- VIRTUALIZATION MODEL: core models are ClusterType/ClusterGroup/Cluster/VirtualMachine/VMInterface. A VirtualMachine must belong to exactly ONE Cluster; official docs explicitly state Nautobot 'does not support pinning a specific VM within a cluster to a particular host device'. Devices are associated to Clusters as hosts (2.x: single Device.cluster FK; 3.0: M2M Device.clusters). There is NO VirtualMachine.device field — unlike current NetBox, which allows assigning a VM directly to a device/site without a cluster. VirtualMachine fields: cluster (required), role, platform, status, tenant, vcpus/memory/disk (annotational), software_version, primary_ip4/6; VMInterfaces carry IPs/VLANs.
- VM-TO-HOST WORKAROUNDS: (a) one Cluster per standalone hypervisor (ClusterType 'Proxmox VE', cluster name = hypervisor hostname, host Device attached) making VM->host implicit — fits the no-shared-storage independent-pair reality; (b) one Cluster per site pair plus a custom Relationship (source virtualization.virtualmachine -> destination dcim.device, one-to-many; Relationships support one-to-one/one-to-many/many-to-many, source/destination filters, 'required' enforcement, REST via /extras/relationship-associations/). Core issue nautobot/nautobot#1178 (unify Device+VirtualMachine via is_virtual flag) remains an open design discussion — no core fix.
- VNF DEVICE-VS-VM: no core mechanism makes a VM also a Device. Community practice (NetBox/Nautobot discussions) is to model hypervisor-hosted VNFs as VirtualMachines with role+platform, using custom fields/relationships for management linkage. Hard constraint discovered: Golden Config scopes devices via Dynamic Groups over dcim.Device and its Nornir inventory is Device-based — VirtualMachines are NOT in scope, so a PA-VM/C8000v modeled only as a VirtualMachine cannot get GC backup/intended/compliance. If GC for VNFs is required, the workaround is a paired Device record linked to the VM by a custom Relationship (dual-record pattern) — otherwise skip GC for VNFs. GC compliance platform list includes paloalto_panos, cisco_ios, cisco_ios_xr, cisco_nxos, arista_eos, linux, etc.
- CONTROLLER MODEL GAP: dcim.Controller (for WLCs/SD-WAN/Panorama-style controllers, capabilities field added 2.4) can only be hosted on a Device (controller_device) or DeviceRedundancyGroup — not on a VirtualMachine. A 9800-CL or SD-WAN controller modeled as a VM cannot anchor a Controller/ControllerManagedDeviceGroup without the dual-record pattern.
- DESIGN BUILDER: nautobot-app-design-builder is genuine and actively maintained — v3.1.0 released 2026-04-20; compatibility matrix: 2.0.X-2.2.X -> Nautobot 2.0.3-2.99, 2.3.X -> Nautobot 2.4.20+, 3.0.X -> Nautobot 3.0.0-3.99. DesignJob subclasses Job (normal Job variables); designs are Jinja2-rendered YAML templates + Context classes (@context_file YAML, validate_* methods raising DesignValidationError) with action tags !create_or_update:field, !update:field, !ref, !git_context, query-field syntax (platform__name), and contrib extensions (BGP, cabling, prefix allocation). Two modes: 'Classic' (ad-hoc, objects unowned) and 'Deployment' (objects owned by a design deployment with a change journal). Deployment mode supports UPDATE (re-run with new inputs; computes adds/removals; requires stable object identifiers across runs) and DECOMMISSION (deletes design-created objects, reverts design-modified objects, dependency-aware; also an unlink-only mode), plus IMPORT of pre-existing objects into a deployment (brownfield). Community size is small: ~15 stars, 24 open issues, 10 forks.
- JOBS MECHANICS (verified against stable docs): register_jobs() required at import time for all Jobs including JobHookReceiver/JobButtonReceiver. Meta attrs: name, description, has_sensitive_variables (defaults True — prevents storing input params in DB), hidden, dryrun_default, soft_time_limit/time_limit (per-job Celery limits, seconds), task_queues (DEPRECATED in 2.4 in favor of job_queues/JobQueue model — queues are Celery or experimental Kubernetes type), is_singleton (2.4+, one concurrent execution, override checkbox exists), console_log_default, field_order. Variable types: StringVar, TextVar, JSONVar, IntegerVar, BooleanVar, DryRunVar, ChoiceVar/MultiChoiceVar, ObjectVar/MultiObjectVar (query_params filtering), FileVar, IPAddressVar/IPAddressWithMaskVar/IPNetworkVar. run() takes keyword args per variable; failure is signaled by raising an exception; logging via self.logger with logger.success (2.4.0+) and logger.failure (2.4.5+), extra={'object': obj, 'grouping': str, 'skip_db_logging': True}; create_file() attaches downloadable outputs to the JobResult; Celery hooks before_start/on_success/on_failure/after_return (must call super()).
- APPROVALS: In 2.x, approval_required + DryRunVar lets dryrun bypass approval (use BooleanVar instead to prevent bypass); JobHookReceiver jobs cannot require approval. In 3.0 approval_required was REMOVED from the Job model — replaced by core multi-stage Approval Workflows (approver groups, N-of-M approvers, approve/deny/comment REST actions under /api/extras/approval-workflow-stages/, permissions extras.change_approvalworkflowstage/view_approvalworkflowstage); a 2.x management command nautobot-server check_job_approval_status identifies jobs still using approval_required before upgrade.
- JOB DELIVERY: a Nautobot Git Repository can provide jobs (jobs/ dir or jobs.py; repository slug becomes the Python module name; module-level code executes at sync — sync permission equals code-execution privilege; newly discovered jobs are DISABLED by default; removed jobs stay in DB with installed=False), config contexts (/config_contexts/ with explicit/implicit/local scoping), config context schemas, export templates, and app-registered types. Private-repo auth via Secrets Group (HTTP(S) token). App-packaged jobs register via NautobotAppConfig.jobs.
- SECRETS/INTEGRATIONS: core Secret model (env-var and text-file providers) + SecretsGroup (access-type/secret-type pairs); nautobot-app-secrets-providers adds HashiCorp Vault, AWS Secrets Manager, Azure Key Vault and its latest major supports Nautobot 3.0/Python 3.13 (previous train for LTM 2.4). Core ExternalIntegration model (since 2.1) stores remote_url, verify_ssl, timeout, headers, extra_config, and a secrets_group, with Jinja2 templating and render_remote_url()/render_headers()/render_extra_config() APIs — designed exactly for jobs reaching external systems (i.e., the right home for Proxmox API and XCC/BMC endpoints instead of free-form job form fields).
- PRIOR ART — PROXMOX: nautobot-app-ssot (latest 4.0.0 -> Nautobot 3.x; 3.10.0 -> LTM 2.4) bundles integrations: Cisco ACI, Bootstrap, Cisco SD-WAN, Citrix ADM, Arista CloudVision, Device42, Cisco DNA Center, Infoblox, IPFabric, Itential, LibreNMS, Meraki, ServiceNow, Slurpit, SolarWinds, vSphere — NO Proxmox integration exists officially. The official vSphere integration does one-way vSphere->Nautobot sync mapping Datacenter->ClusterGroup, Cluster->Cluster, VM->VirtualMachine, VM NIC->VMInterface, plus IPs — the canonical template for a future Proxmox DiffSync adapter. Community repos: fadenb/nautobot-ssot-proxmox (2 stars, 7 commits, updated Aug 2025, Nautobot 2.x, single cluster only, VM/LXC matched by proxmox_vmid custom field, no interfaces, deletions off by default) and HarbourHeading/nautobot-ssot-proxmox (1 star). netbox-proxbox is NetBox-only with a FastAPI backend architecture — not portable to Nautobot.
- SOFTWARE VERSIONS: since Nautobot 2.2, dcim.SoftwareVersion and dcim.SoftwareImageFile are CORE models applicable to Devices, InventoryItems, and VirtualMachines (ported from the DLM app; DLM 3.0 ships a migration job from its legacy SoftwareLCM models). Device Lifecycle Management app latest is 4.0.0 (Nautobot 3.x; 3.2.X for Nautobot 2.4.20+) and layers EoL/EoS, validated-software, and contract tracking on the core models. nautobot-app-firewall-models latest major requires Nautobot 3.0 (previous major maintained for LTM 2.4) if PA policy modeling is ever wanted.
- CONFIG CONTEXTS: scoped to locations, roles, device types, device families, device redundancy groups, platforms, cluster groups, CLUSTERS, tenant groups, tenants, tags, and dynamic groups; weight-based hierarchical merge (dict deepmerge, list replacement); apply to BOTH Devices and VirtualMachines; per-object local context always wins; manageable in-UI or via Git repo; Config Context Schemas (JSON Schema) validate shape. Suitable for per-site VLAN maps, NIC tuning values, serial-console/OpenGear parameters, rendered in jobs via obj.get_config_context().

## Recommendations for This Project

- Decide platform version first: greenfield should target Nautobot 3.x (GA since Nov 2025; all required official apps have Nautobot-3 trains: SSoT 4.0, Golden Config 3.0, DLM 4.0, secrets-providers, firewall-models, design-builder 3.x); if the org standardizes on LTM 2.4 instead, pin the matching app trains (GC 2.6.x, SSoT 3.10.0, DLM 3.2.x, design-builder 2.3.X) — the approval mechanism and job-queue APIs differ between 2.4 and 3.x, so job code should be written against one target.
- Model each SE350 as its own one-host Cluster (ClusterType 'Proxmox VE', cluster name = hypervisor hostname, host Device attached, ClusterGroup per site holding the pair): encodes VM->host implicitly without custom Relationships, matches the no-shared-storage/no-PVE-cluster reality, works identically on 2.4 and 3.x, and is what a future Proxmox SSoT adapter would naturally target.
- Model VNFs (PA-VM, C8000v, 9800-CL, SD-WAN edge, jump host) as VirtualMachines with Role + Platform (napalm/netmiko-style platform names, e.g. paloalto_panos, cisco_ios_xe) + core SoftwareVersion, IPs on VMInterfaces, primary_ip set — do NOT create Device records for them in phase 1; introduce the dual-record (Device + custom Relationship to VM) pattern only if/when Golden Config compliance for VNFs becomes a requirement, because Golden Config cannot scope VirtualMachines.
- Solve the 'site design' problem in phase 1 with a hand-written idempotent Job (site code + supernet + server1/2 ObjectVar/StringVar inputs; pure functions computing the IPAM/VLAN/device/VM layout, then get_or_create-style application), and run a bounded spike on nautobot-app-design-builder deployment mode in parallel — it is actively maintained (v3.1.0, 2026-04-20) and its update/decommission/import lifecycle directly matches the lab-build/field-redeploy/RMA-rebuild scenarios, but its small community and YAML-DSL learning curve make it a phase-2 adoption decision, not a phase-1 dependency. Structure the phase-1 job so the layout-computation layer could be re-emitted as a design template later.
- Job architecture: many small composable jobs (create/update site design; deploy hypervisor node; deploy single VM; redeploy VM) rather than one monolith; put DryRunVar on every data-mutating job; JobButtonReceiver jobs on Device/VirtualMachine detail pages for field one-off redeploys; per-job soft_time_limit/time_limit and a dedicated JobQueue (worker) for long node-level deploys; is_singleton on per-node deploy jobs to prevent concurrent runs against the same box; keep the colleague's split of pure client library (xcc_client) vs Job wrapper.
- Record orchestration state in Nautobot as: Status values (create custom Statuses scoped to dcim.device and virtualization.virtualmachine, e.g. Planned/Installing/Active/Failed — 3.0's Device statuses plus custom ones), a small number of custom fields for machine-readable state (e.g. provisioning_stage, last_deploy_job_result UUID), Notes for human annotations, and the JobResult itself for logs/artifacts (create_file for generated answer.toml/bootstrap ISO manifests); avoid inventing a parallel state store until an App with real models is justified.
- Replace free-form BMC-IP/ISO-URL job inputs with Nautobot-native references: ObjectVar(Device) for the target node, ExternalIntegration objects (remote_url + SecretsGroup) for the XCC/Redfish endpoint and the Proxmox API, and SecretsGroup-attached Secrets (env-var provider now, nautobot-app-secrets-providers/Vault later) — this also removes the hardcoded Secret-name lookups in the current xcc_deploy job.
- Deliver jobs via a Nautobot Git Repository now (fast iteration, matches colleague's repo intent) and graduate to a packaged Nautobot App when any of these appear: custom models/migrations, REST/UI views, shared client libraries used by multiple repos, or the need for pinned Python dependencies — Git-synced jobs cannot declare pip dependencies, an App can.
- Keep per-site/per-role tuning data (VLAN maps, NIC tuning, power/serial/OpenGear parameters, oversubscription policy) in Git-managed config contexts with Config Context Schemas for validation, scoped by Location/Role/Platform/Cluster; have jobs render Jinja2 (answer.toml, PA bootstrap, cloud-init) from get_config_context() output rather than hardcoding values in job code.
- Defer any Proxmox->Nautobot reconciliation (drift sync) to a later phase; when wanted, write a DiffSync adapter inside the nautobot-app-ssot framework modeled on the official vSphere integration (ClusterGroup/Cluster/VM/VMInterface/IP mapping); treat fadenb/nautobot-ssot-proxmox and HarbourHeading/nautobot-ssot-proxmox as reference reading only (toy-scale, no releases, 2.x-targeted).

## Pitfalls & Gotchas

- Nautobot core cannot pin a VM to a host Device inside a multi-host cluster — if the pair is modeled as ONE cluster, VM->host mapping must live in a custom Relationship that no other app (SSoT, GC, export templates) understands natively; the one-cluster-per-host pattern avoids this but means 'cluster' in Nautobot != 'cluster' in Proxmox terminology (these SE350s are standalone PVE nodes anyway, so the term collision is cosmetic).
- Nautobot 3.0 REMOVED Job.approval_required — any job code, docs, or runbooks written against 2.x approval semantics break on 3.x; DryRunVar's approval-bypass behavior is a 2.x-only concern; plan approvals via 3.x Approval Workflows (permission model changed to extras.*_approvalworkflowstage).
- Git-synced job gotchas: module-level code executes during repo sync (sync permission == code execution — restrict extras.change_gitrepository); jobs arrive DISABLED and must be enabled per-job; the repository slug becomes the Python module path, so renaming the repo/slug changes job identity, orphaning JobResult history and Job settings (overrides, schedules, buttons).
- Golden Config is Device-only (Dynamic Group of dcim.Device + Nornir device inventory): VNFs modeled as VirtualMachines are invisible to it. Budget for either the dual-record pattern or accepting no GC compliance on VNFs; also note GC 'linux' platform exists but running GC against Proxmox hosts themselves (as Devices) needs a custom dispatcher.
- Celery default soft/hard time limits (CELERY_TASK_SOFT_TIME_LIMIT default 300s / TIME_LIMIT 600s unless overridden) will kill long node-install or VM-deploy jobs that poll — set per-job soft_time_limit/time_limit or (better, per the colleague's pipelines plan) keep Nautobot jobs as fast dispatch/verify steps and let an external orchestrator own multi-stage waits.
- has_sensitive_variables=True (the default) blocks storing job inputs, which disables re-run convenience and scheduling of those jobs — explicitly set it False on jobs whose inputs are non-sensitive (target device, site code); conversely never route credentials through job variables at all (Secrets/ExternalIntegration).
- Design Builder deployment-mode updates assume object identifiers (the !create_or_update keys) stay identical across runs and list ordering is stable; renaming a site code or device naming convention between runs breaks the diff/ownership model, and the import feature cannot reconstruct prior values. Its community is small (~15 stars) — treat it as a leveraged bet with an exit path (plain ORM job), not a foundation.
- dcim.Controller cannot be hosted on a VirtualMachine — modeling the 9800-CL WLC or an SD-WAN controller function via Controller/ControllerManagedDeviceGroup requires a Device record; if APs/edges managed by these controllers are ever modeled, this gap forces the dual-record pattern for the controller VMs.
- Nautobot 3.0 REST API excludes many-to-many fields by default (exclude_m2m) and standardized several filters — existing pynautobot scripts and GraphQL/dynamic-group filters may silently change behavior after upgrade (run nautobot-server validate_models extras.dynamicgroup extras.savedview post-upgrade).
- The colleague's job uses self.logger.failure / self.logger.success — these only exist as of Nautobot 2.4.5 / 2.4.0 respectively; on earlier 2.x they raise AttributeError. Also its Secret lookup is by bare name and its BMC target is a free IPAddressVar with no Device linkage, so runs are not traceable to a Device record — no state is written back to Nautobot on success.

## Open Questions

- Which platform train will the org run: Nautobot 3.x (current, Bootstrap-5 UI, approval workflows) or LTM 2.4 (critical-fixes-only apps)? Every subsequent choice (approval design, app versions, job APIs) forks on this; needs a user decision before job code is written.
- Design Builder v3.1.0 (2026-04-20) Nautobot compatibility ceiling: the published matrix shows the 3.0.X train covering Nautobot 3.0.0-3.99.99 but the 3.1.0 entry itself was not directly verified against pyproject — confirm in a lab before committing, along with whether its Deployment-mode journal performance is acceptable at 'one deployment per site' scale.
- Is Golden Config compliance for the VNF configs (PAN-OS, IOS-XE) actually a requirement? If yes, the Device-vs-VM dual-record decision must be made in the initial data model, since retrofitting Relationships onto hundreds of existing VMs is painful.
- Did Nautobot 3.1 (April 2026) change anything in the virtualization model (VM->device assignment, NetBox-parity)? Docs verified here still state pinning is unsupported as of the stable docs consulted, but 3.1-specific release notes were not exhaustively reviewed — worth a 10-minute check of the 3.1 release notes before finalizing the cluster-per-host pattern.
- Whether devices attached as cluster hosts must share the Cluster's Location (docs imply location consistency checks exist) — affects whether lab-staged builds (scenario 1: built in lab, shipped to site) can be created directly under the destination site Location or need a staging Location plus a move step; verify in a lab.
- Quality/reusability of fadenb/nautobot-ssot-proxmox and HarbourHeading/nautobot-ssot-proxmox code (small, unreleased): needs code review before any reuse decision; neither is verified against Nautobot 3.x or SSoT 4.0.
- Whether the org wants Nautobot Approval Workflows gating destructive jobs (field VM redeploy on in-service hypervisors) from day one — 3.x makes this a first-class core feature, but it adds operator friction in the lab as-built scenario; needs a workflow-policy decision.
