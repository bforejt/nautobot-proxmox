# NFV Edge Lifecycle Process Design

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

The mature pattern for this team is a two-plane architecture: a "design job" (Nautobot Design Builder or a hand-rolled equivalent) that takes exactly the three legacy operator inputs (site code, subnets, server 1/2) and materializes all intent into Nautobot, plus a small set of idempotent per-layer deploy jobs that read only from the SoT and push to devices with zero questions asked. All three scenarios (lab as-built, field VM redeploy, lab rebuild after failure) then collapse into one code path entered at different layers, because each layer job converges actual state toward SoT intent rather than executing a scripted sequence. Orchestration should start as plain Nautobot Jobs on a dedicated long-running celery queue (per-Job time_limit overrides exist; the celery hard default is only 10 min) with status written back to Nautobot custom fields; an external runner (AWX via the Nautobot Ansible Automation app, or GitHub Actions) is a later optimization, not a prerequisite. Proxmox's auto-installer natively provides the layer-boundary plumbing (HTTP answer fetch keyed on DMI serial/MAC, post-installation webhook, first-boot hooks), which strongly favors one generic ISO + answer service over per-node ISOs.

## Key Findings

- Intent/imperative split has a first-class Nautobot implementation: nautobot-app-design-builder (actively maintained: v3.0.0 Nov 2025 adds Nautobot 3.0 compat, v3.1.0 Apr 2026). Designs are text templates (YAML/Jinja) exposed as Nautobot Jobs; a 'design deployment' is a tracked instantiation with full lifecycle: all created objects are grouped as one entity, can be updated or decommissioned as a unit, and design-owned data is protected from out-of-band modification. This maps 1:1 onto the legacy robot's questions: site code + subnets + server-1/server-2 become design job inputs; the design job creates devices, interfaces, VLANs, prefixes/IPs (standard IPAM carve), VMs, and per-server one-off skip logic in the SoT; deploy jobs then take a Device/VM reference and no other input.
- The Network to Code 'design-driven NSoT' pattern (Jan 2025 blog) documents the exact target workflow: minimal-input design jobs generate thousands of related objects as a cohesive unit; deployment to devices happens either via GitOps review of rendered changes or directly via renderers like Golden Config; principles include complete CRUD on the deployment as a unit, versioned designs, and brownfield import of existing sites into design ownership.
- Intended-vs-actual compliance loop is the industry-standard follow-on: Nautobot Golden Config implements backup -> intended (render from SoT) -> compliance diff -> auto-generated remediation (hier_config) -> config plans gated by approval. It is network-CLI-oriented, so for Proxmox hosts the same loop must be implemented as a custom 'audit/compliance' job that reads actual state via the Proxmox API and diffs against SoT intent - but the loop shape (never 'run a script', always 'converge toward intent, report drift') is the pattern to copy.
- One-code-path-for-three-scenarios is achieved by layering, not by scenario playbooks. Standard layering for this stack: L0 bare-metal (Redfish virtual media + auto-install ISO - already working in colleague's repo for SE455 V3), L1 host baseline (power/CPU governor, NIC tuning, serial console redirect, repos, SSH keys), L2 network fabric (LACP bond, VLAN-aware bridge or bridge-per-VLAN from Nautobot VLAN data), L3 VM provisioning (clone golden template, vNICs/VLAN tags, autostart order, resource pins), L4 VNF day-1 (cloud-init for Ubuntu, bootstrap ISO for PA VM-Series, config-drive/CLI bootstrap for C8000v/9800-CL), L5 handoff to per-VNF orchestrators (Panorama/SCM, vManage, Catalyst Center/WLC GUI) - after which per-VNF config is explicitly NOT this system's job. New-office build = L0-L5 in lab; hardware-failure rebuild = identical L0-L5 in lab against the same (already-existing) SoT intent; field VM redeploy = L3-L4 only against one VM. Each layer job must be idempotent (safe to re-run on a converged host) and independently invokable with only a Device/VM reference.
- Proxmox auto-installer natively supports the layer boundaries: (a) --fetch-from http makes the installer POST JSON with DMI serial/UUID/SKU + all NIC MACs to an answer service, enabling ONE generic ISO for the whole fleet with per-node answer.toml generated from Nautobot data (keyed on serial or MAC); (b) [post-installation-webhook] (PVE 8.3+) POSTs machine-id, SSH host keys, disks, NICs to a URL with optional auth-token and cert-fingerprint pinning - a ready-made L0-complete status write-back event; (c) [first-boot] hooks run a script/binary (from-iso or from-url, max 1 MiB, ordering before-network/network-online/fully-up) - the natural place to pull and execute L1/L2 baseline or to phone home for the next stage. PVE 9.2-1 adds subscription-key in the answer file and auth-token for webhooks.
- Nautobot Jobs ARE viable for long stages if configured: celery hard time limit defaults to 10 minutes globally (SIGKILL) with a configurable soft limit (SoftTimeLimitExceeded), but Job Meta supports per-job soft_time_limit/time_limit overrides. Official guidance for long-running jobs: run a dedicated worker on a separate JobQueue so long jobs never starve Nautobot's default celery queue (system tasks share it). Jobs can chain via JobResult.enqueue_job (enqueued on DB commit), and Nautobot 2.4+ adds a JobQueue model with 'celery' and 'kubernetes' types (k8s = dispatch jobs as short-lived pods; experimental in 2.4).
- Human checkpoints exist natively: approval_required on scheduled jobs, and Nautobot 3.x adds multi-stage Approval Workflows attachable to models. Hard constraint: a Job with has_sensitive_variables=True cannot be scheduled or approval-gated (its vars must persist in the DB), so credentials must come from Nautobot Secrets, never job inputs - the colleague's xcc_deploy job already follows this (has_sensitive_variables=False, Secrets looked up at runtime).
- External-runner integration is productized if/when needed: the 'Nautobot Ansible Automation' app imports AWX/AAP job templates into Nautobot's Jobs UI (disabled by default per template), runs them remotely, and streams results back into Nautobot Job Results - operators keep a single pane of glass. Alternative trigger paths: Nautobot webhooks with Jinja bodies -> AWX, or Event-Driven Ansible rulebooks consuming Nautobot events.
- Secrets: Nautobot's Secret model stores a retrieval pointer, never the value; nautobot-app-secrets-providers supports HashiCorp Vault (token/approle/aws/kubernetes auth, multiple vault configs) plus AWS/Azure/etc.; Secrets Groups can mix backends per secret. This supports per-site or per-tier BMC credentials for field devices without code changes.
- Image/artifact SoT is built into Nautobot core since 2.2: dcim.SoftwareVersion (per Platform, EoS dates, LTS/pre-release flags) and dcim.SoftwareImageFile (file name, checksum + hashing algorithm, size, download_url, status) associate to Devices AND VirtualMachines - the correct place to record golden qcow2/template versions and vendor VNF images (PA VM-Series, C8000v, 9800-CL are entitlement-gated manual downloads; record checksum at ingest, verify at deploy).
- Golden template builds: HashiCorp Packer's proxmox-iso/proxmox-clone builders create PVE templates via the API; common practice is CI-scheduled rebuilds with version tags and qemu-img convert to qcow2. For vendor VNFs (no Packer possible), 'ingest' = upload vendor qcow2 to an internal artifact store + import as PVE template + record SoftwareImageFile; for Ubuntu, bake the desktop/jump-host golden template once and clone + cloud-init per node (colleague's repo already plans this).
- Proxmox Datacenter Manager reached stable 1.0 in Dec 2025; 1.1 released May 2026 (1.1.7 July 2026). It is now a legitimate fleet-visibility layer for many small unclustered nodes, but its API-token permission scoping still has rough edges (colleague's repo notes an unresolved 403 on PDM enrollment).
- Repo reality check (paths under /private/tmp/claude-501/-Users-brianforejt-Documents-code-nautobot-proxmox/ac27099e-ee7c-4648-8b56-d4992cdca713/scratchpad/repo-layout/repo-layout/): jobs/xcc_deploy is a clean fire-and-forget L0 trigger (Redfish mount + boot-once + power cycle) that deliberately ends with 'poll Proxmox mgmt IP separately' - i.e., L0 completion detection is currently manual; the post-installation-webhook finding above closes that gap. pipelines/README already states the correct philosophy (Nautobot Job stays fast/re-runnable; long multi-stage work dispatched externally with status written back to custom fields). The job targets SE455 V3; SE350 (this project's hardware) is an older EOL platform with an earlier XCC generation - Redfish virtual-media capabilities must be re-validated on SE350 firmware.

## Recommendations for This Project

- Adopt the design-job/deploy-job split as the architectural spine now, even before adopting Design Builder itself: one 'Site NFV Design' job takes site code + subnets + server-1/2 and writes ALL intent to Nautobot (devices, IPAM carve, VLANs, VMs with per-server skip logic, naming); every other job takes only a Device/VM selector and reads intent from the SoT. Why: this single decision is what makes the three scenarios one code path and eliminates the interactive robot's question-answering forever.
- Structure deploy automation as per-layer idempotent jobs (L0 bare-metal, L1 host baseline, L2 bridges/bonds, L3 VM provision, L4 VNF day-1) each runnable standalone, plus a thin 'site build' wrapper that runs them in sequence with a stage checkpoint written to a Device custom field (e.g., provisioning_state: bm_installed -> baseline_done -> fabric_done -> vms_deployed -> handed_off). Why: field redeploy is then just 'run L3+L4 for this one VM', and a failed site build resumes at the failed layer instead of restarting.
- Keep orchestration inside Nautobot Jobs for phase 1: create a dedicated JobQueue + one extra celery worker for long deploy jobs, set per-Job soft_time_limit/time_limit generously (e.g., 3600/5400 s), and chain stages with JobResult.enqueue_job rather than one monolithic hour-long run. Why: a small network team should not operate AWX/K8s just to get started; Nautobot's own primitives (queues, per-job limits, chaining, approval gates) cover an hour-long site build, and the external-runner escape hatch (Nautobot Ansible Automation app, or the experimental k8s JobQueue) remains available unchanged later because jobs are already layer-scoped.
- Resolve the ISO decision in favor of ONE generic auto-install ISO with --fetch-from http and a small answer service that renders answer.toml from Nautobot data keyed on DMI serial/MAC (the installer POSTs both), and add [post-installation-webhook] + a [first-boot] from-url hook to the answer file. Why: per-node ISO builds add a build-and-host step per server and drift risk; the generic-ISO pattern turns L0 completion into an event (webhook receiver updates provisioning_state and can enqueue L1) instead of a human polling the mgmt IP.
- Make lab-first a hard rule: scenarios 1 and 3 (new build, failure rebuild) always execute L0-L5 in the lab staging network where Nautobot has direct reachability and blast radius is zero; field operations over WAN are restricted to L3/L4 VM-level actions on in-service hosts, gated by Nautobot approval (approval_required / 3.x Approval Workflows) and preceded by an automated pre-flight job (peer VM of the redundant pair healthy? config backup/snapshot taken? console path via OpenGear verified?). Why: this matches how the team already works, keeps the risky path narrow, and makes the WAN-reachability question (direct vs jump host) only relevant for the small L3/L4 surface - which flows through the Proxmox API on the host, reachable via the existing management path.
- Track every golden template and vendor VNF image in core Nautobot SoftwareVersion/SoftwareImageFile with checksum + hashing algorithm at ingest time, and have the L3 deploy job verify the checksum of the template/image on the target host before cloning. Why: vendor images (PA/Cisco) are manual, entitlement-gated downloads, so the SoT record is the only automatable integrity/version control point; it also gives per-VM 'built from image X' provenance for failure rebuilds.
- Phase the adoption by toil-per-risk: (1) design job + IPAM/naming materialization (pure SoT writes, zero device risk, kills the most error-prone manual work); (2) L0+L1 lab-only bare-metal pipeline with webhook status write-back (already half-built in the colleague's repo); (3) L3/L4 golden-template VM deploy in lab; (4) drift/compliance audit job (read-only against field hosts - builds trust in the SoT before any field writes); (5) field L3/L4 redeploy with approval gates; run the ESXi robot untouched for existing sites and cut over per-site (new builds and rebuilds go Proxmox first), never converting in-service ESXi hosts in place. Why: each step is independently valuable, read-only-before-write builds operator trust, and per-site cutover means the old process remains the rollback for the fleet.
- For field-redeploy rollback: rely on the redundant-pair design as the primary guardrail (never automate simultaneous actions on both servers of a pair - enforce in code: refuse to touch server 2's twin VM if server 1's is not healthy), keep the replaced VM's disk/config as a renamed artifact on local storage until the new VM passes post-deploy checks, and keep the OpenGear/serial console path as the documented out-of-band recovery. Why: with no shared storage, the pair IS the HA mechanism, and the cheapest rollback is 'the old VM still exists, powered off'.
- Re-validate the SE350's XCC Redfish virtual-media support with current (final) firmware in the lab before assuming the SE455 V3 job ports over. Why: SE350 is EOL with an older XCC generation; virtual-media Redfish behavior differs across XCC firmware levels, and this is the foundation of L0.

## Pitfalls & Gotchas

- Celery hard time limit defaults to 10 minutes and kills jobs with SIGKILL and no exception - an hour-long site-build job will silently die mid-flight unless per-Job time_limit/soft_time_limit are set; and any long job on the default queue starves Nautobot's own background tasks (the docs explicitly warn about this).
- has_sensitive_variables=True disables both scheduling and approval workflows for a job - if any deploy job takes a credential as an input variable, the approval-gate strategy for field operations breaks; all credentials must flow through Secrets/Secrets Groups.
- Design Builder's data-protection model means design-owned objects resist out-of-band edits - a benefit, but a trap if the team half-adopts it: manual fixes to design-owned Nautobot objects during an incident will conflict with the design deployment. Decide up front whether Design Builder owns the data or whether a hand-rolled design job (plain ORM writes, no ownership enforcement) is the phase-1 fit, upgrading later.
- The Proxmox HTTP answer-fetch flow is a POST of system info, not a simple GET - the answer service must parse the JSON (DMI serial, MACs) and render per-node TOML; naive static file hosting only works with one file per URL. Also note first-boot from-url executables are capped at 1 MiB (use it as a fetch-and-exec stub, not a payload).
- The post-installation webhook and answer service invert connectivity: the SERVER being built must reach the webhook/answer endpoints. Fine in the lab staging network; for any future field bare-metal reinstall it becomes a WAN-reachability and TLS problem (mitigations exist: cert-fingerprint pinning, DHCP option 251, auth-token in PVE 9.2+). Lab-first sidesteps this entirely - do not accidentally design a field bare-metal path.
- Job chaining via enqueue_job gives sequencing but not durable pipeline state - if the worker restarts between stages, nothing resumes automatically. The provisioning_state custom field must be the source of resume truth (each job checks it on entry and no-ops already-completed work), otherwise 'resumable' is fiction.
- The Nautobot Ansible Automation app requires job templates to pre-exist in AWX/AAP and needs network reachability Nautobot->AWX; it is an interface, not an orchestrator-builder - adopting it means operating AWX too, which is real ongoing load for a small network team.
- Kubernetes JobQueue execution is marked Experimental (introduced 2.4.0) - do not build the phase-1 architecture on it.
- PDM API token permission scoping is still immature (the repo's own unresolved 403 on enrollment) - treat PDM as visibility, not as an orchestration dependency.
- Idempotency is hard at L2 specifically: re-running bridge/bond changes on an in-service host can bounce links carrying live VNF traffic. L2 jobs need a diff-then-apply pattern (compute delta vs /etc/network/interfaces or SDN config, apply only if changed, never blind-rewrite) - this is the layer where 'idempotent' must mean 'no-op when converged', not 'safe to reapply'.
- Running old ESXi and new Proxmox processes side by side means two naming/IPAM conventions may coexist; if the design job's standard IPAM carve differs at all from the ESXi robot's, per-site records must tag which convention a site uses or field troubleshooting gets dangerous.

## Open Questions

- Does the SE350's XClarity Controller (final EOL firmware level) support the same Redfish virtual-media mount + boot-once semantics the SE455 V3 job uses? Lab verification required; this gates reuse of jobs/xcc_deploy.
- Design Builder vs hand-rolled design job for phase 1: does the team want Design Builder's ownership/protection semantics (and its learning curve, plus coupling to its release cadence) now, or plain ORM-writing design jobs first with a later migration? Needs a user decision after a lab spike.
- Where does the answer-service + webhook receiver run? Options: a tiny Flask/FastAPI sidecar next to Nautobot (renders answer.toml from Nautobot API, receives post-install webhook, enqueues next-stage job via Nautobot API) vs. serving answers from a Nautobot Job-backed custom API endpoint. The sidecar is simple but is a new always-on component to operate.
- What is the actual management-plane reachability from Nautobot to field sites today (direct routed mgmt VRF? per-site jump host? OpenGear OOB only)? This determines whether field L3/L4 jobs can use the Proxmox API directly or must proxy, and what the secrets story is for per-site access.
- Team's secrets backend of record: is there an existing Vault (or equivalent) to point nautobot-app-secrets-providers at, or does phase 1 accept env-var Secrets on the celery worker (as the colleague's repo does) with a planned migration?
- Which Nautobot version is the team on / targeting? 3.x (Nov 2025+) brings multi-stage Approval Workflows relied on above; 2.4 is the floor for JobQueue. Design Builder v3.x requires Nautobot 3.0 compatibility alignment.
- Per-VNF day-1 handoff boundaries: exactly which orchestrator claims each VNF (SCM vs Panorama for VM-Series; vManage/SD-WAN Manager for C8000v controller mode; what for 9800-CL and autonomous C8000v?) - determines where L4 ends per VNF type and what minimal bootstrap each needs.
- Are there any field sites where a bare-metal reinstall over WAN would ever be attempted (vs. always shipping a lab-rebuilt replacement)? The recommendation assumes never; if wrong, the answer-service/webhook connectivity design changes materially.
- Cutover policy question for the transition period: when a legacy ESXi site has a hardware failure, is the replacement rebuilt as ESXi (old process) or as Proxmox (making failures the organic migration driver)? Affects how long both processes must be maintained and how the pair (one ESXi + one Proxmox host?) would interoperate - mixed pairs may be unacceptable for the redundant-VM model.
