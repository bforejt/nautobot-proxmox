# VNF Guest Requirements on Proxmox/KVM

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

All five VNF guests are deployable on Proxmox/KVM with one common skeleton: import a vendor qcow2 as the boot disk, give the VM virtio NICs/disk (CPU type host, serial0 added), then attach a small generated CD-ROM ISO carrying the day-0 payload — only the ISO payload format differs per guest (Palo bootstrap-package directory tree, Cisco iosxe_config.txt, vManage-generated ciscosdwan_cloud_init.cfg, or Proxmox's own auto-generated cloud-init NoCloud ISO for Ubuntu). Cisco officially supports generic KVM; Palo Alto qualifies specific Linux/KVM distros and Proxmox VE is NOT on its compatibility matrix, though community recipes for PAN-OS 11.2.x on Proxmox (q35+SeaBIOS+virtio) are well documented. The generalized Nautobot job pattern "deploy VM from image + optional bootstrap ISO + serial console + pinned MAC/UUID" covers all five workloads.

## Key Findings

- Palo Alto VM-Series (PAN-OS 11.x/12.1 era): ships as a single qcow2 for KVM (PA-VM-KVM-x.y.z.qcow2). Fixed models: VM-50 2vCPU/5.5GB/32GB(60GB at boot), VM-100 2vCPU/6.5GB/60GB, VM-300 2-4vCPU/9GB/60GB, VM-500 2-8vCPU/16GB/60GB, VM-700 2-16vCPU/56GB/60GB; flexible-vCPU models funded by Software NGFW credits also exist. PAN-OS 11.1+ needs more memory for the same session scale as pre-10.2.
- VM-Series on KVM NIC support: virtio and e1000 are supported on Linux bridge/OVS; the QEMU default rtl8139 is NOT supported. Compatibility matrix lists 'DPDK with Virtio' and 'Packet MMAP with Virtio' modes. Newest qualified stacks: PAN-OS 11.2.x on RHEL 9.5/9.6, PAN-OS 12.1.x exists (12.1.7 listed, incl. RH OpenStack 18). Proxmox VE is not listed anywhere in the qualified-hypervisor matrix.
- VM-Series on Proxmox community recipe (packetswitch 2024/25 with PAN-OS 11.2.5, cdot65 gist, Proxmox forum thread 101431): machine q35 + SeaBIOS, CPU type host, virtio-scsi-pci controller but boot disk attached as virtio0 via 'qm importdisk <id> PA-VM-KVM-11.2.5.qcow2 <storage>', virtio NICs, serial0 socket; create the VM with NO disk and import the qcow2. Older PAN-OS/PVE combos required pinning the machine version (pc-q35-8.0) — default i440fx and newest q35 both failed at one point; treat machine-version pinning as part of the guest profile.
- VM-Series bootstrap: CD-ROM ISO (attached as IDE CDROM) or an ext3 block disk <39GB. Package root must contain all four dirs /config, /license, /software, /content (even if empty); /plugins and /ace optional. /config holds init-cfg.txt (+ optional bootstrap.xml); /license takes an auth-code bundle. init-cfg.txt key fields: type=static|dhcp-client, ip-address/netmask/default-gateway, hostname, dns-primary/secondary, panorama-server (or panorama-server=cloud for Strata Cloud Manager), panorama-server-2, tplname, dgname, vm-auth-key (Panorama), vm-series-auto-registration-pin-id/-value (required for SCM/device cert), op-command-modes (jumbo-frame, multi-vsys), plugin-op-commands.
- VM-Series licensing is node-locked to the VM's UUID+CPUID (serial number derives from them); if Proxmox regenerates the SMBIOS UUID on a rebuild the license/serial breaks and requires PAN support to re-map — pin smbios1 UUID (qm set --smbios1 uuid=...) from Nautobot for the field-rebuild scenario. Palo also warns each deployed instance must keep its own independent copy of the qcow2 (no sharing one image file across instances).
- Catalyst 8000v autonomous: download options are .qcow2 (including a separate '_serial' qcow2 variant whose console is on the serial port) or .iso. KVM supports virtio vNICs, max 26 vNICs/VM (17.4+). Footprints: 1-4 vCPU need >=4GB RAM, 8-16 vCPU need >=8GB (16 vCPU from 17.11.1a); Service-Plane-Heavy (UTD/SNORT, AppQoE) needs 8vCPU/16GB. Working virt-install pattern: --machine q35, disk bus=virtio format=qcow2, --network model=virtio, --cpu host-passthrough, --graphics none --console pty,target_type=serial --boot hd,useserial=on. Console selectable at GRUB on first boot or via 'platform console serial|virtual'.
- Catalyst 8000v day-0 (private cloud/KVM): attach a CD-ROM containing iosxe_config.txt (raw IOS CLI) or ovf-env.xml; a config-drive style second disk/CD-ROM is also supported. Three bootstrap input formats exist: custom-data, user-data, and SDWAN (ciscosdwan_cloud_init.cfg). Config is applied at first boot.
- Catalyst 8000v licensing: ships with a built-in shaper limiting throughput to 10 Mbps until 'platform hardware throughput level MB <x>' is set; Smart Licensing Using Policy (17.3.2+) is trust/report-based; throughput >250 Mbps of crypto requires an HSECK9 SLAC. Current releases: 17.18.x is the last 17.x train (17.18.1a/17.18.2/17.18.3a; release notes updated May 2026; adds Ubuntu 22.04 LTS and RHEL 9.6 hypervisor support and ConnectX-6/7 SR-IOV); Cisco moved to unified numbering with IOS XE 26.1.1 (GA April 2026).
- Catalyst 8000v SD-WAN controller mode: same image/binary as autonomous. If a ciscosdwan_cloud_init.cfg (software devices; ciscosdwan.cfg for hardware) is found at a bootstrap location (CD-ROM ISO in KVM labs, or bootflash + 'controller-mode enable' which erases NVRAM and reloads), the router flips to controller mode and applies it. The file is a vManage/SD-WAN-Manager-generated cloud-init MIME multipart (cloud-config with vinitparam+root CA, plus cloud-boothook device config). All four of otp, uuid, vbond, org must be present or the device boots autonomous. UUID comes from the WAN-edge provisioning/serial file tied to the Smart Account.
- Legacy vEdge Cloud is dead: end-of-sale May 2, 2023, last software 20.9.x (Viptela OS, different image and bootstrap) — do not build tooling for it; C8000v controller mode is the replacement.
- Catalyst 9800-CL: ships as .qcow2 or .iso (also OVA for ESXi); KVM deployment documented with virt-manager/virt-install/virsh; set every vNIC Device model to virtio. Scale templates: Small 4vCPU/8GB (1000 APs/10k clients), Medium 6vCPU/16GB (3000 APs/32k clients), Large 32GB (6000 APs/64k clients; sources disagree 10 vs 16 vCPU); 16GB disk for all. Standard 3-vNIC layout: Gi1=device management (OOB, service-port equivalent), Gi2=wireless management (usually a dot1q trunk, carries CAPWAP), Gi3=HA SSO RP (omit if no SSO). Console: VGA by default, switch with 'platform console serial'; a virtual serial console can be added in KVM.
- Catalyst 9800-CL day-0: official paths are the CLI wizard or the Day-0 web GUI (https://<mgmt IP>). The IOS-XE iosxe_config.txt-on-CD-ROM method (mkisofs an ISO with the file at root) works and is documented by third parties; known quirk: on first boot the full output and CLI input are only on the VNC/VGA console even if 'platform console serial' is in the bootstrap config — reboot after day-0 for serial. AP join on the -CL additionally requires: 'wireless country XX' (radios stay down without it), a reachable wireless management interface (WMI), and a self-signed cert generated via 'wireless config vwlc-ssc key-size 2048 signature-algo sha256 password 0 <pw>' (hardware 9800s have a MIC; the virtual one does not; avoid '$' in the password). Licensing is Smart Licensing Using Policy (usage-report based, not enforced at join).
- Ubuntu on Proxmox: Proxmox native cloud-init generates an ISO attached as a CD-ROM (conventionally ide2 <storage>:cloudinit), NoCloud datasource for Linux (ConfigDrive2 for Windows, citype selectable). Provisioning knobs: qm set --ciuser/--cipassword/--sshkeys/--ipconfig0 ip=CIDR,gw=.../--nameserver/--cicustom 'user=<snippets>,network=...,meta=...'. Image import: qm importdisk or qm set --scsi0 <storage>:0,import-from=<path>. Recommended: --serial0 socket --vga serial0 (many cloud images expect serial). Golden pattern: import Ubuntu Server cloud image (qcow2 .img from cloud-images.ubuntu.com), qm template, then qm clone + per-clone ipconfig. No official Ubuntu Desktop cloud image exists — bake desktop/remote-access tooling into the template once (matches the colleague's ubuntu/README plan).
- Proxmox mechanics relevant to all guests (pve-docs chapter-qm, PVE 8/9): default machine type is i440fx, q35 only needed for PCIe passthrough (but PAN-OS community recipes use q35); virtio NIC ~3x e1000 throughput; multiqueue: set queues = vCPU count on the NIC, Linux guests must enable via ethtool -L (Cisco/PAN guests manage their own queues); MACs are auto-generated unless set statically in net0=virtio=<mac> — pin MACs from Nautobot so rebuilds preserve NIC identity; virtio-scsi-single with iothread is the default/recommended controller since PVE 7.3; CPU type host recommended for single-host (no live-migration) deployments — matches the SE350 pair model; machine version pinning controls hardware enumeration stability across PVE upgrades. NIC PCI ordering follows net0..netN, which is what maps to PAN-OS mgmt->ethernet1/1... and IOS-XE Gi1..GiN — never hot-add NICs to these guests, redeploy instead.
- Day-0 injection comparison — the common abstraction holds: every guest = (1) upload/import vendor qcow2 -> VM boot disk; (2) optionally attach ONE generated CD-ROM ISO whose payload is guest-specific: VM-Series = ISO with /config/init-cfg.txt(+bootstrap.xml)/license/software/content tree; C8000v autonomous = ISO with iosxe_config.txt at root; C8000v SD-WAN = ISO with ciscosdwan_cloud_init.cfg at root; 9800-CL = ISO with iosxe_config.txt at root (plus post-boot wireless cert/country steps); Ubuntu = Proxmox-native cloudinit drive (Proxmox builds the NoCloud ISO itself from qm options/snippets). (3) serial console + onboot=1. So one Nautobot job with a per-VNF 'iso_builder' plugin (Jinja2 -> genisoimage -> upload to ISO storage via API -> attach ide2) plus a 'native-cloudinit' builder for Ubuntu covers everything; day-N onboarding (SCM/Panorama, SD-WAN Manager, AP join, licensing) is carried inside the day-0 payloads themselves (panorama-server=cloud + registration PINs, vm-auth-key, otp/uuid/vbond/org, wireless cert commands).

## Recommendations for This Project

- Build ONE generic 'deploy VM from qcow2 + optional bootstrap ISO' Nautobot job with per-VNF profile objects (cpu/ram/disk, machine type+pinned version, bios, nic list with bridge/VLAN/queues/pinned MAC, serial0, onboot) and a pluggable iso_builder — the research confirms all five guests fit this shape; only the ISO payload template differs.
- Use virtio NIC + virtio disk + CPU type host for every guest — officially supported for all four vendor VNFs on KVM and 3x faster than e1000; the no-live-migration SE350-pair design removes the usual reason to avoid CPU host.
- Pin identity in Nautobot and push it into Proxmox at create time: static MACs per vNIC and SMBIOS UUID per VM (qm --smbios1 uuid=) — this makes scenario 3 (lab rebuild after hardware failure) license-safe for VM-Series, whose serial is derived from UUID+CPUID, and keeps IOS-XE interface numbering deterministic.
- For VM-Series use q35 + SeaBIOS + virtio0 imported disk with a pinned q35 machine version validated per PAN-OS release; keep the bootstrap ISO to /config/init-cfg.txt with panorama-server=cloud + vm-series-auto-registration-pin-id/value for SCM onboarding (matches the palo-vm/README plan of minimal bootstrap.xml + SCM-central policy).
- For C8000v download the '_serial' qcow2 variant (console on serial out of the box — aligns with the OpenGear emergency-console requirement) and drive day-0 with an iosxe_config.txt ISO in autonomous mode or the unmodified SD-WAN-Manager-generated ciscosdwan_cloud_init.cfg ISO in controller mode — same job, different template.
- For 9800-CL deploy small template (4vCPU/8GB/16GB disk) with the canonical 3-vNIC layout (Gi1 mgmt, Gi2 wireless trunk, Gi3 HA or omit) and include in day-0: platform console serial, wireless country, WMI config, and the vwlc-ssc self-signed-cert command — these four are the difference between 'VM boots' and 'APs join'.
- For Ubuntu skip custom ISO building entirely: use Proxmox native cloud-init (template + clone + qm set ipconfig0/sshkeys/cicustom snippets) — it is the same CD-ROM mechanism under the hood but Proxmox generates it, so model it as a second builder type ('native-cloudinit') in the generic job rather than a special case.
- Target software: PAN-OS 11.2.x KVM qcow2 (newest broadly qualified 11.x; 12.1 exists if SCM features demand it), IOS-XE 17.18.x for C8000v and 9800-CL (last 17.x extended-maintenance train, current as of mid-2026) — but let SD-WAN Manager version compatibility gate the controller-mode C8000v build, and confirm AP model support gates the 9800-CL release.
- Set explicit throughput day-0 on C8000v ('platform hardware throughput level MB ...') because the image boots with a 10 Mbps shaper; plan the HSECK9 SLAC workflow now if any site needs >250 Mbps IPsec.
- Do not build anything for vEdge Cloud (EoS 2023, last SW 20.9.x); C8000v controller mode is the only SD-WAN edge worth automating.

## Pitfalls & Gotchas

- Proxmox VE is absent from Palo Alto's qualified-hypervisor compatibility matrix (only specific Ubuntu/RHEL/SUSE/OpenStack KVM stacks are listed) — VM-Series on Proxmox works and is widely deployed, but TAC can point at the matrix; decide the support posture consciously.
- PAN-OS machine-type sensitivity on Proxmox: history of boot failures on default i440fx and on too-new q35 versions, fixed by pinning pc-q35-8.0 (PVE 8.1 era); newer PAN-OS 11.2.5 guides use plain q35 — validate and pin the machine version per PAN-OS release, and re-test on PVE major upgrades since unpinned Linux-type VMs silently move to the newest machine version.
- VM-Series serial/license breaks if SMBIOS UUID or CPUID changes (VM rebuilt without pinned UUID, or moved to different CPU) — the portal shows serial 'unknown' and only PAN support can re-map it; also PAN-OS applies the change on reboot, so it can surface days later.
- rtl8139 (QEMU default in some tools) is explicitly unsupported by VM-Series; and each firewall instance must have its own copy of the qcow2 — no shared backing file.
- C8000v boots throttled to 10 Mbps and stays there until throughput level is configured; >250 Mbps crypto silently requires an HSECK9 SLAC (extra licensing workflow, painful in air-gapped labs).
- SD-WAN bootstrap fails silently: if any of otp/uuid/vbond/org is missing or unreadable the C8000v just boots autonomous mode with no error banner; also the file name must be exactly ciscosdwan_cloud_init.cfg for software devices, and 'controller-mode enable' wipes NVRAM.
- iosxe_config.txt is consumed on FIRST boot only — a failed day-0 needs a fresh disk (redeploy) rather than a re-run; design the job as destroy-and-recreate, which also matches the golden-image philosophy.
- 9800-CL first-boot output/input lands on the VNC/VGA console even when 'platform console serial' is in the bootstrap config — serial-only operator procedures will look hung until after the post-day-0 reboot; and APs will not join without wireless country, reachable WMI, and the vwlc-ssc self-signed cert ('$' in the cert password hits a parsing bug).
- 9800-CL large-template vCPU count is inconsistently reported (10 vs 16) across sources; small template numbers (4/8GB/1000 APs) are consistent — size from the official install guide for the chosen 17.x release, not blogs.
- Never hot-add/remove NICs on the IOS-XE and PAN-OS guests: interface naming follows PCI enumeration order (net0..netN), so topology changes renumber Gi1..GiN / ethernet1/x; recreate the VM instead.
- Proxmox multiqueue (queues=vCPUs) only helps if the guest enables the queues; for Linux jump hosts you must ethtool -L in the image; for VNFs verify vendor guidance before enabling — and cipassword in cloud-init is stored in the VM config, prefer SSH keys; cicustom snippets must live on a snippets-enabled storage present on the target node.
- Cisco.com documentation pages block automated fetching (403) — the exact official wording for some day-0 details (ISO volume label requirements, config-drive labeling) could not be pulled; lab-verify before hardcoding assumptions.

- Is iosxe_config.txt-via-CD-ROM officially supported for the 9800-CL on KVM, or an inherited-but-undocumented IOS-XE behavior? It works per community guides; confirm Cisco TAC supportability before making it the production path.
- Exact 9800-CL large-template vCPU count (10 vs 16) and the recommended IOS-XE release for the team's specific AP models — needs the official install guide table for the chosen release.
- PAN-OS target: 11.2.x vs 12.1.x, fixed model (VM-100/300?) vs flexible-vCPU Software NGFW credits, and SCM vs Panorama onboarding — drives which init-cfg.txt fields the template needs (vm-auth-key vs auto-registration PINs).
- Which q35 machine version boots the chosen PAN-OS cleanly on Proxmox VE 9.x — needs a lab matrix test (history of version-specific breakage).
- How C8000v software-device UUIDs get allocated in this org (Smart Account provisioning file -> SD-WAN Manager WAN edge list) and which Manager version constrains the 17.18/26.x image choice.
- Serial-console strategy for C8000v: use the '_serial' qcow2 variant vs standard image + 'platform console serial' in day-0 — pick one and standardize (affects golden-image inventory).
- Whether VM-Series on KVM has a hard per-VM interface cap relevant to the SE350 design (not verified this pass), and whether PAN-OS DPDK-on-virtio needs tuning/disabling (plugin-op-commands dpdk) on Proxmox bridges.
- Whether the team wants the Ubuntu jump host as Desktop (golden template only, no cloud image exists) or Server+RDP/VNC tooling on the standard cloud image — affects whether the Ubuntu path is pure clone+cloud-init or template-bake plus cloud-init.
