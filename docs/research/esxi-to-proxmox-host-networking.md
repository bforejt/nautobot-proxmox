# ESXi → Proxmox Host Networking & Tuning

> Reference document from the project research pass (August 2026). Claims were verified
> against vendor documentation current at that time; version-specific facts should be
> re-checked before implementation. Items needing hands-on confirmation are consolidated
> in [plan-of-attack.md §6](../plan-of-attack.md).

## Summary

Every element of the ESXi host-prep flow has a clean Proxmox VE 9.x equivalent, and most of it (bonds, bridges, VLANs, VM NIC trunking, autoboot ordering, VM serial consoles) is drivable through the REST API with no SSH. The recommended networking model for this use case is one LACP bond + one VLAN-aware Linux bridge, with VM NICs using tag= for access ports and no-tag/trunks= for full or filtered dot1q trunks to VNFs that self-tag (PA-VM, C8000v); OVS and SDN zones are unnecessary for standalone edge pairs. The gaps the API cannot cover — kernel cmdline (C-states, hugepages, serial console), ethtool offload/ring tuning, and GRUB serial redirect — are exactly the pieces that should land in the proxmox-install firstboot hook rather than a post-hoc SSH robot. Basic-capability-first: adopt cpu=host, NUMA flag, multiqueue, offload disabling, onboot/startup ordering, serial0 socket now; defer per-vCPU pinning and hugepages until a measured need appears.

## Key Findings

- Networking model mapping: ESXi vSwitch+port groups maps to ONE VLAN-aware Linux bridge (vmbr0) on top of a bond. A VM NIC with tag=<1-4094> is an ESXi access port group; a VM NIC with NO tag on a VLAN-aware bridge receives the full trunk (all VLANs allowed by bridge-vids, default 2-4094) — this is the ESXi VLAN-4095/VGT equivalent for PA-VM and C8000v that do their own tagging; trunks=<vid;vid;...> (semicolon-separated) restricts that trunk to a subset. Exact net option syntax from qm.conf(5): net[n]: [model=]<enum> [,bridge=..] [,firewall=1|0] [,mtu=..] [,queues=<int>] [,tag=<int>] [,trunks=<vlanid[;vlanid...]>].
- bridge-vids on a VLAN-aware bridge defaults to 2-4094 — VLAN 1 tagged is NOT passed by default; bridge_vids is settable via GUI/API ('2 4 100-200' range syntax) to whitelist the site's IPAM-derived VLAN set for hygiene.
- OVS guidance (Proxmox wiki Open_vSwitch): use Linux bridge unless you specifically need OVS features (port mirroring, per-port features, EVPN); never mix OVS constructs with Linux bonds/bridges/VLANs in one stack. Proxmox SDN (chapter-pvesdn) VLAN zones are a cluster-wide abstraction (/etc/pve/sdn) layered on an existing local bridge per node; vnets carry a single tag and are not the trunk-to-VM model — for standalone (non-clustered) edge pairs SDN adds indirection with no benefit today.
- LACP bond: /etc/network/interfaces pattern is 'auto bond0 / iface bond0 / bond-slaves eno1 eno2 / bond-mode 802.3ad / bond-miimon 100 / bond-xmit-hash-policy layer3+4' then 'auto vmbr0 / iface vmbr0 / bridge-ports bond0 / bridge-vlan-aware yes / bridge-vids ...'. PVE 9 uses ifupdown2 (default since PVE 7.0); apply live with ifreload -a; never plain ifup/ifdown.
- Network REST API (verified from apidoc.js schema): POST /nodes/{node}/network creates iface configs with type in {bridge, bond, eth, alias, vlan, fabric, OVSBridge, OVSBond, OVSPort, OVSIntPort, vnet}; parameters include slaves, bond_mode (enum incl. 802.3ad), bond_xmit_hash_policy (layer2|layer2+3|layer3+4), bond-primary, bridge_ports, bridge_vlan_aware, bridge_vids, cidr/gateway (v4+v6), mtu, autostart, vlan-id, vlan-raw-device. Changes are STAGED to /etc/network/interfaces.new; PUT /nodes/{node}/network ('Reload network configuration') applies them via ifupdown2 and returns a task UPID; DELETE /nodes/{node}/network reverts staged changes; PUT /nodes/{node}/network/{iface} edits one iface. Requires Sys.Modify on /nodes/{node}; all endpoints allow API tokens (allowtoken=1). So bonds/bridges/VLANs are fully creatable and appliable with zero SSH.
- Network API limits (from the same schema): no bond-lacp-rate, no bond-min-links, no post-up/pre-up hook lines, no ethtool/ring/txqueuelen/offload knobs, no arbitrary stanza text; iface names are 2-20 chars. PVE preserves 'source' directives in /etc/network/interfaces but does not read or manage sourced files (they are invisible to GUI/API); custom post-up lines inside PVE-managed stanzas generally survive rewrites but are not updated when interfaces are renamed via GUI.
- Power policy: ESXi 'High Performance' splits into two layers on Lenovo+Proxmox. Firmware: Lenovo UEFI 'Operating Modes -> Choose Operating Mode -> Maximum Performance' (settable via XCC, OneCLI/ASU, or Redfish BIOS attributes — belongs in the repo's bmc/ BIOS policy). OS: Proxmox kernels with intel_pstate already default the scaling governor to 'performance'; the latency lever that actually matters for VNFs is C-state depth — add intel_idle.max_cstate=1 processor.max_cstate=1 to the kernel cmdline (idle=poll is the extreme version, not appropriate for an edge thermal envelope).
- Kernel cmdline persistence on PVE 9 has TWO paths: GRUB installs edit /etc/default/grub GRUB_CMDLINE_LINUX_DEFAULT then update-grub; UEFI+ZFS-root installs (common with the automated installer) use /etc/kernel/cmdline + proxmox-boot-tool refresh instead. Automation must handle both.
- NIC offloads: Palo Alto's official KVM host tuning for VM-Series is 'ethtool -K <data-if> rx off tx off tso off ufo off gso off gro off lro off' on host data interfaces — GRO/LRO coalesce frames into oversized super-packets that a bridged router/firewall VM then drops or must re-segment, so they must be off in the bridged-VNF path (LRO is the hard requirement, GRO/TSO the strong recommendation). Cisco's C8000v KVM guide adds: use hugepages, emulator pinning, nmi_watchdog=0, transparent_hugepage=never, NUMA tuning, pin all vCPUs to one socket, and warns that unreliably-scheduled vCPUs cause packet drops/outages.
- Multiqueue virtio-net: per-VM NIC option queues=<N>; Proxmox docs and PA docs both say set N = number of vCPUs (PA: match dataplane cores); guest must activate with 'ethtool -L <if> combined N' (PAN-OS/IOS-XE handle their own dataplane); it raises host CPU load, so only set on dataplane NICs.
- No native Proxmox persistence mechanism exists for ethtool/txqueuelen tuning: the three patterns are (a) post-up lines in /etc/network/interfaces stanzas (executed by ifupdown2, re-run on ifreload), (b) a sourced file under /etc/network/interfaces.d (preserved but unmanaged/invisible to GUI), (c) a systemd oneshot unit or udev rule — (c) is the most robust target for automation because it is independent of PVE's interfaces parser.
- VM autoboot: onboot: <boolean> (default 0) plus startup: [order=]N[,up=secs][,down=secs]; executed per-node by pve-guests.service at boot — lower order first, 'up' seconds waited before starting the next guest, shutdown in reverse order; guests without startup start after all ordered ones. qm set <vmid> --onboot 1 --startup order=1,up=30. HA-managed guests ignore onboot/startup entirely (irrelevant here — standalone hosts, no cluster/HA). This maps 1:1 to ESXi VM autostart + start delay.
- Host serial console for OpenGear: firmware layer — SE350 UEFI 'Devices and I/O Ports -> Console Redirection Settings' (COM1 enable, baud, emulation), configurable via XCC/OneCLI/Redfish so it belongs in bmc/ BIOS policy; OS layer — console=tty0 console=ttyS0,115200n8 on the kernel cmdline (systemd then auto-spawns serial-getty@ttyS0, no manual getty needed) plus GRUB_TERMINAL/GRUB_SERIAL_COMMAND if the boot menu itself must be reachable; persistence via the same dual GRUB/proxmox-boot-tool paths above. XCC IPMI Serial-over-LAN exists as an alternative OOB path.
- VM serial consoles: serial[n] accepts exactly (/dev/[^,]+|socket) — 'qm set <vmid> -serial0 socket' creates a UNIX socket at /var/run/qemu-server/<vmid>.serial0, attached via 'qm terminal <vmid>' (Ctrl-O exits) or the GUI xterm.js console; a VM serial port CAN alternatively be mapped to a host physical port (serial0: /dev/ttyS1) to hard-wire one VM to an OpenGear line. Guests need console=ttyS0 (Linux) or platform console serial (Cisco). Practical emergency path: OpenGear -> host ttyS0 login -> qm terminal <vmid>.
- CPU pinning/NUMA/hugepages: affinity: <cpulist> (e.g. 0,5,8-11) is implemented with taskset and constrains the whole VM to those host cores — it is NOT per-vCPU 1:1 pinning (no virsh-vcpupin equivalent without hookscripts). hugepages: <2|1024|any> plus keephugepages: <bool>; hugepages requires the VM's NUMA flag enabled and is restricted to root@pam (so NOT settable via an API token — a real constraint for Nautobot-driven automation). cpu type 'host' is the documented recommendation when live migration between heterogeneous nodes is not needed — exactly this deployment (identical standalone pairs).
- SE350 (original, Xeon D-2100 family) is single-socket/single-NUMA-node, so Cisco's cross-socket pinning warnings and NUMA topology tuning are moot on this hardware; enabling the VM numa flag is still harmless and future-proofs configs for other platforms.
- ESXi features with NO direct Proxmox equivalent: (1) port-group security policies (promiscuous mode / forged transmits / MAC address changes) — a Linux bridge does no MAC anti-spoofing by default, so the old 'enable forged transmits for VNF port groups' step simply disappears; the inverse control is the PVE firewall's per-NIC MAC/IP filter, so keep firewall=0 (or add exceptions) on VNF NICs carrying VRRP/HSRP/PA-HA floating MACs; (2) per-port-group uplink failover-order overrides — a Linux bond's policy is bond-wide; (3) vmkernel NICs — the mgmt IP just lives on the bridge or a VLAN sub-interface of it; (4) CDP/LLDP on vSwitch — install lldpd on the host if neighbor visibility from the upstream switch is required.
- Proxmox capabilities that delete parts of the old ESXi robot: golden-VMDK deploy is replaced by qcow2 VM templates + clone (or qm disk import) via API; Ubuntu jump hosts move to native cloud-init support (no golden-image mutation robot); the automated-installer answer.toml + firstboot hook can pre-bake bond/bridge config and kernel-cmdline/serial/ethtool tuning at install time; qemu-guest-agent reports VM IPs back for Nautobot reconciliation; nearly the whole post-install robot becomes API-token calls (network staging+reload, VM create/clone/config, onboot/startup) with SSH needed only for the few host-OS file edits — which belong in firstboot anyway.

## Recommendations for This Project

- Standardize on bond0 (802.3ad, bond-xmit-hash-policy layer3+4, bond-miimon 100) + one VLAN-aware bridge vmbr0 with bridge_vids set to the site's Nautobot-derived VLAN list — simplest 1:1 ESXi mapping, fully API-creatable; skip OVS and SDN zones for standalone edge pairs.
- Model VM NICs from Nautobot as: tag=<vid> for access-port VNF interfaces, no tag (or trunks=<list>) for PA-VM/C8000v trunk interfaces — prefer explicit trunks= lists generated from IPAM data over open all-VLAN trunks for auditability.
- Drive all bond/bridge/VLAN provisioning through POST /nodes/{node}/network + PUT /nodes/{node}/network (apply) with an API token holding Sys.Modify — keep the DELETE (revert) call as the rollback path in the Nautobot Job; do not SSH for L2 provisioning.
- Put the non-API host tuning (kernel cmdline: intel_idle.max_cstate=1 processor.max_cstate=1, console=tty0 console=ttyS0,115200n8; ethtool offload-off systemd unit for data NICs; lldpd) into the proxmox-install/ firstboot hook, because these are one-time, reboot-coupled, and outside the API's reach.
- Put 'Choose Operating Mode = Maximum Performance' and 'COM1 Console Redirection = enabled' into the bmc/ Redfish BIOS policy — they are firmware halves of the old ESXi power-policy and serial-redirect steps and pair naturally with the existing XCC job.
- VM profile baseline now: cpu type host, numa=1, queues=<vCPU count> on dataplane NICs, onboot=1 with startup order (e.g. PA-VM order=1,up=120; C8000v order=2 ...), serial0=socket on every VNF; defer affinity pinning and hugepages to a later phase triggered by measured jitter/throughput problems.
- Disable the PVE firewall (firewall=0) on VNF dataplane NICs from day one so floating/virtual MACs (VRRP, PA-VM HA) are never silently filtered.
- Have the deployment job assert governor==performance and C-state cmdline at verify time (read /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor, /proc/cmdline) rather than assuming defaults, since ZFS-root vs GRUB installs persist cmdline differently.

## Pitfalls & Gotchas

- hugepages and keephugepages are restricted to root@pam AND require the VM numa flag — a Nautobot Job authenticating with an API token cannot set them; if hugepages are ever adopted, that step needs root SSH or a firstboot-provisioned VM template default.
- VLAN 1 tagged is excluded by the default bridge-vids 2-4094; any design using tagged VLAN 1 must add it explicitly.
- trunks= uses semicolons (10;20;30); in shell/Ansible contexts the semicolons need quoting, and the Proxmox GUI historically exposes trunks only in the config/CLI, not the NIC dialog.
- The network API stages changes to interfaces.new — forgetting the PUT (reload) call leaves the node half-configured; conversely a bad staged config is recoverable with DELETE (revert) only BEFORE apply. A wrong bond/bridge apply on the mgmt path can strand a remote node: sequence mgmt-affecting changes so the serial/OpenGear path is proven first.
- Custom post-up/ethtool lines placed inside PVE-managed interface stanzas are preserved on rewrite but not tracked by GUI/API renames; sourced files are preserved but invisible to the GUI — prefer a systemd oneshot for tuning to avoid both failure modes.
- Offload state does not survive some ifreload/link-bounce sequences depending on driver — re-assert ethtool settings via post-up or a unit ordered after network-online, not just once at install.
- update-grub does nothing useful on UEFI+ZFS-root installs (systemd-boot path): kernel cmdline lives in /etc/kernel/cmdline and needs proxmox-boot-tool refresh — an automation that only edits /etc/default/grub will silently fail to persist C-state and serial-console settings on installer-imaged nodes.
- affinity is taskset-based whole-VM confinement, not per-vCPU pinning — it prevents noisy-neighbor core sharing but does not give Cisco's 'each vCPU on its own dedicated core' guarantee; treating it as equivalent may under-deliver for jitter-sensitive dataplanes.
- qm terminal detach is Ctrl-O, which collides with nano's save keybinding — worth a note in runbooks.
- PVE-firewall MAC/IP anti-spoof filtering only engages when firewall=1 on the NIC, but templates/clones can carry firewall=1 silently — audit generated configs.
- Multiqueue queues= adds host CPU load per queue; setting it on every NIC of every VM on a small Xeon D erodes the deliberately-limited oversubscription budget — restrict to dataplane NICs.

## Open Questions

- Whether qm 'affinity' can be set by a non-root API token in PVE 9.x (hugepages is documented root-only; affinity's privilege requirement was not confirmed from official docs) — verify in lab with the actual token role before phasing pinning in.
- Exact surviving-rewrite semantics of custom post-up lines when the SAME stanza is later edited via the network API (preserved vs dropped) in PVE 9 — forum evidence is mixed and version-dependent; a 10-minute lab test decides whether tuning can live in interfaces stanzas or must be a systemd unit.
- Whether the original SE350's UEFI (UEFI_IOT firmware family) exposes the same 'Choose Operating Mode = Maximum Performance' preset and COM1 console-redirection attributes over Redfish as newer ThinkSystem models, and the exact Redfish attribute names — needs a live XCC BIOS-attribute dump on real SE350 hardware (Lenovo pubs confirm the settings exist in the F1 menu; Redfish attribute naming unverified).
- Whether PAN-OS VM-Series' in-guest DPDK default on virtio changes the multiqueue recommendation (PA docs say match dataplane cores; whether queues>dataplane-cores wastes host CPU on PA-VM specifically) — verify against the deployed PAN-OS version's tuning guide.
- Node-level 'startall-onboot-delay' (delay before pve-guests starts any VM, useful to let switch LACP converge before VNFs boot) — believed available via pvenode config; confirm presence/name in PVE 9 before relying on it.
- Whether the team ever used ESXi per-port-group uplink failover overrides (active/standby per port group); if yes, that pattern needs a redesign (multiple bonds or acceptance of bond-wide policy) since Linux bonds cannot express it per-VLAN.
